Status: **everything is built and checked offline. Nothing has run on the phone.** The camera probe switches the 2.8 V camera rail (gpio51) and the MCLKs, so **it must be attended**.

The upstream IMX576 v4 patch could not be downloaded. lore, patchwork and ratatoskr all block non-browser clients from WSL and from the container. I wrote our own IMX576 driver from the stock register tables instead. Its full mode matches the upstream v4 link rate: 1011 MHz on 4 lanes.

## 1. Wiring (stock DT `qcom,cci@ca0c000` + `vendor/etc/camera/camera_config.xml` + `sensor_lib_t` in the vendor libs)

| | IMX576 (rear main) | Hi-846 (rear wide) | S5K3T1 (front) |
|---|---|---|---|
| Stock slot / DT node | camera@0 | camera@1 | camera@2 |
| CCI master / 7-bit addr | 0 / **0x1a** (lib 0x34) | 1 / **0x20** (xml 0x40; lib says 0x42, but the xml overrides it) | 1 / **0x2d** (lib 0x5a) |
| Chip ID | reg 0x0016 = 0x0576 | 0x0f16 = 0x0846 | reg 0x0000 = **0x3141** (read from lib header) |
| MCLK | gpio32 MCLK0, 24 MHz | gpio34 MCLK2, 24 MHz | gpio33 MCLK1, 24 MHz |
| Reset | gpio46 | gpio48 | gpio47 |
| CSIPHY / stock CSID | 0 / 0 | 1 / 2 | 2 / 1 |
| Lanes | **4** (LaneMask 0x1F, LaneAssign 0x4320 = straight) | **4** (the earlier overlay said 2, which was wrong) | **4** |
| Bayer order (default orientation) | RGGB | GBRG | GRBG |
| Stock power-up sequence (lib, ms) | RST low 1, VANA 1, MCLK 2, RST high 3 | VANA 0, MCLK 5, RST low 1, RST high 5 | RST low 1, VANA 5, RST high 5, MCLK 2 |
| Exposure margin (lib) | 61 lines | 6 | 8 |
| Stock modes | 5760x4312@30 (OP 2022 Mbps/lane), 2880x2156@30 (510 Mbps/lane), @60, 2880x1620@90, 2880x2156@120 | 3264x2448 | **2304x1728@30 only** (2x2 binned from a 4608x3456 crop, 564 Mbps/lane) |
| Actuator | **GT9769** on CCI0 **0x0c** (lib 0x18). 10-bit, init 02=02 06=61 07=39, position = word to reg 0x03 | none | none |
| EEPROM | `imx576_hmct_eeprom` (not used) | yes | yes |

Rails:
- VANA and VAF share one fixed 2.8 V regulator with enable on **gpio51**, fed from pm660l_bob. Stock names the voltage oddly (1.78–1.95 V in the index table), but the regulator itself is fixed at 2.8 V.
- DVDD and DOVDD are not in stock DT or in the lib power sequences, so they are board rails. The overlay uses always-on dummy regulators for them.
- The mount angle is 90 for both rear cameras and 270 for the front camera.
- Flash is on PM660L (see rest doc).

How the drivers are built:
- The drivers are generated from one template: `research/cam-20260924/gen.py` + `template.c`, modelled on mainline `s5kjn1.c`.
- They replay the stock init and res tables verbatim (IMX576: 302 init regs + per-mode ~76–134 regs; S5K3T1: 585 init regs incl. a firmware patch and a 3 ms soft-reset delay, + 79 mode regs).
- Controls: LINK_FREQ, PIXEL_RATE, HBLANK, VBLANK, EXPOSURE (0x0202), ANALOGUE_GAIN (0x0204), TEST_PATTERN (0x0600), H/VFLIP, and rotation/orientation from DT.

## 3. Attended test (ATTENDED ONLY: camera rail + MCLK; no RF, no flash writes)

Prerequisite: boot a V75 image whose DTB has `a6l-camera-v75.dtbo` merged. The flash agent builds it with `fdtoverlay -i v74.dtb -o v75cam.dtb a6l-camera-v75.dtbo`. The kernel must be the v67/7.2.3-a6l-probe build, the same vermagic as the V74 recovery.

1. Push the bundle: `adb push ~/A6L-usb-20260915/v75/camera /tmp/camera`.
2. `adb shell 'export PATH=/tmp/bin:$PATH; D=/tmp/camera MODE=dt sh /tmp/camera/run-camera.sh'` → expect 4× `DT_NODE_PASS`.
3. `... MODE=probe ...` → expect these markers:
   - `IMX576_PROBE_PASS` (dmesg `Sony IMX576 chip id 0x576`)
   - `S5K3T1_PROBE_PASS` (`chip id 0x3141`)
   - `HI846_PROBE_PASS` (`chip id 46 08 using 4 mipi lanes`)
   - `GT9769_PROBE_PASS`
   - `/dev/media0`, 4+ `/dev/v4l-subdev*` for the sensors and VCM, and `msm_vfe0_video*`.

   On failure:
   - A chip-ID mismatch prints the value that was read. This matters most for S5K3T1, whose ID is unverified.
   - `-ENXIO`/`-EREMOTEIO` means wrong address or no power. Watch Pierre's phone: no heat; the rail is only 2.8 V.
4. `MODE=list` shows the media topology. Confirm that `msm_csiphy0..2`, `msm_csid0..3`, `msm_ispif0..3` and `msm_vfe0_rdi0` exist.
5. `SENSOR=hi846 MODE=bars`: test pattern, needs no optics. Expect `CAPTURE_hi846_bars_PASS`. Then pull the frame and convert it: `python3 raw10_to_png.py cam-hi846-bars.raw 1632 1224 <bpl> GBRG out.png` should show colour bars. Repeat `SENSOR=imx576` and `SENSOR=s5k3t1` with `MODE=bars`.
6. `MODE=live` for each sensor. Adjust `EXP`/`GAIN` (env) if the image is black or white.
7. `MODE=focus`: sweeps the VCM 0→1023→0. Pierre listens for a faint click or looks at the lens.

After any sensor test: `rmmod imx576_a6l s5k3t1 hi846 gt9769` powers the rail down via runtime PM.

## 4. Risks
- **IMX576 full mode is 2.02 Gbps/lane.** sdm660 CSIPHY 3ph-1.0 in mainline may not settle at that rate. The default mode is therefore the 2x2 binned 2880x2156 mode at 510 Mbps/lane. The binned-mode link rate (255 MHz) is derived from `op_sys_clk_div=4`, but the QC lib reported 250.8 Mpix/s (≈627 Mbps/lane). If CSID reports CRC/ECC or no SOF, change `link_freq_menu[0]` to 313500000.
- The Samsung OP post-divider (0x0312 = 2, read as /4) was chosen so that the QC `op_pixel_clk` of 225.6 Mpix/s matches exactly.
- The S5K3T1 chip ID 0x3141 comes from the lib header and has not been confirmed by a read.
- The GT9769 has no ID check. The init values are exactly stock, and the part is written only after VAF is on.
- DVDD/DOVDD are assumed to be always-on board rails. If the chip-ID read times out while gpio51 is high, a PMIC LDO may feed the sensors. Stock never switches one, so this is unlikely.
- All sensors share one AVDD. Runtime PM refcounts it, but all three probing at once draws the most current. No risk is expected beyond stock behaviour.

## 5. Unknowns
- EEPROM/OTP addresses and formats: needed later for lens shading and AWB calibration. `libmmcamera_*_eeprom.so` holds the parsers.
- Hi-846 in 4-lane mode with the upstream driver has only the 1280x720 and 1632x1224 modes. The upstream 640x480 default is 2-lane only, so the test forces 1632x1224. Stock runs 3264x2448 at 750 Mbps/lane; its table is in `research/cam-20260924/tables/hi846_*.txt` if a full-res mode is wanted.
- Chromatix → libcamera tuning is not done. The CCM was not found as float or Q7/Q8/Q10 3x3 matrices in `libchromatix_*_{common,preview}.so`. It is probably in the 3A libs (`*_3a.so`) or in a chromatix 0x0310 struct that needs its header. **Next:** decode `libchromatix_imx576_hmct_9ak04b_default_preview_3a.so` (AWB reference points, gains) and `*_preview.so` (LSC 17x13 grids) against a leaked chromatix_0310 header. Until then use libcamera's `uncalibrated.yaml` for the simple IPA.

## 6. Android HAL plan
- `external/libcamera` in the Lineage tree is the AOSP snapshot `3ab4b94` (26Q2, version string 0.1.0). It has the `qcom-camss` simple-pipeline entry but **no `software_isp` and no `ipa/simple`**. The Android.bp builds only the `virtual` pipeline.
- Without SoftISP, CAMSS gives raw Bayer only, which is useless for the camera3 HAL. **Required:** replace it with upstream libcamera ≥ 0.7, which has the simple pipeline, SoftISP with the GPU (EGL/GLES 3.x) debayer (freedreno GLES 3.1 should do) and the simple IPA with AGC/AWB/CCM/LSC-lite.
- Suggested route: build upstream with meson + NDK r27c as a prebuilt:
  - `-Dandroid=enabled -Dandroid_platform=generic -Dpipelines=simple -Dipas=simple -Dsoftisp=enabled`
