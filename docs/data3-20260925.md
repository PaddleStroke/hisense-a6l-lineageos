## 0. Summary
| question | answer |
|---|---|
| Why does rmnet_ipa0 show `tx 3 / tx_drop 3`? | **These are two different sets of 3 packets, and neither is test traffic.** `rmnet_ipa0` is `ARPHRD_RAWIP`, and 7.2 addrconf autoconfigures RAWIP devices (`net/ipv6/addrconf.c:2413,3498`). When the netdevs came up, the kernel sent IPv6 RS/MLD/DAD packets. The ones sent on **rmnet_ipa0 itself** have `skb->protocol = ETH_P_IPV6`, so `ipa_ndev_start_xmit()` drops them because it only accepts `ETH_P_MAP`. That is the only place `tx_dropped++` happens: **tx_drop 3**. The ones sent on **rmnet_data0** were QMAP-wrapped by rmnet and went through pipe 4: **rmnet_data0 tx 3 → rmnet_ipa0 tx 3 (TX completions) → pipe 4 rd = wr = 0x18 = 3 descriptors consumed**. The IPA took all three. The call was IPv4-only (`mtu6=0`), so the modem drops IPv6 anyway. |
| Why is RX empty? | **No IPv4 packet was ever sent.** `ip`/`route` are missing in the recovery, and toybox `ping` only opens SOCK_DGRAM ICMP, which failed with "Permission denied" (ping_group_range). So no route was added and no echo was sent; `A6L_QMI_DATA_DNS_PASS` only means the modem returned DNS addresses. Nothing solicited a reply. Pipe 5 wr 0x07f8 = 255 RX buffers posted with rd 0 = the ring is armed and nothing has arrived. `irq 0x4` = the P_WAKE bit, which is normal. |
| Is the TX path wrong? | Not proven. The QMAP header on EP4 (hdr 0x44 = len 4, metadata at offset 0), WAN RX (0x002800c4 / 0x0b / mask 0xff000000), EP4 route 7, and the modem-owned EP4 filtering (stock DT `qcom,modem-cfg-emb-pipe-flt`) all match downstream. No aggregation is needed on EP5: IPA v2 DL aggregation is set by the AP on EP5 (reset value = bypass). The WDA `dl=5 dl_max 31/63` only allows the modem to aggregate, and rmnet de-aggregates single or aggregated QMAP frames with ingress flag 0x01. |
| Real defects found and fixed in ipa2_lite | (1) **EP4 default route index 7 pointed at the SRAM canary.** EP4 `ENDP_INIT_ROUTE` = 7 (downstream `v4_apps_rt_index_lo`), but upstream ipa2-lite allocates only 7 route entries (0..6). Word 7 (0x364) is the canary `0xdeadbeaf` before the v6 table (layout test). Any UL packet that no modem filter rule matches used a garbage table. Now 8 entries, index 7 = empty table → the IPA_ROUTE default pipe 2 (ipa_lan0, exception), and the modem is still told 0..6. (2) **The AP QMI server ignored modem requests.** Downstream ipa_v2 answers `INSTALL_FILTER_RULE` 0x23, `FILTER_INSTALLED_NOTIF` 0x24 and `CONFIG` 0x27, even with emb-pipe filtering (it replies success and installs nothing). ipa2-lite registered only 0x20, and its server receive buffer was **8 bytes**. The modem therefore never got an ack for its UL filter rules, and it is not known whether it activates UL forwarding without one. Now all three are answered, logged as `A6L_IPA qmi …`, with a 33712-byte buffer. |
| Diagnostics added | `A6L_IPA_ST` decodes, in dmesg, the IPA v2 **status packet** of every AP TX packet (EP4 sends its status to EP2 = ipa_lan0): source and destination pipe, exception, filter/route table/rule, match bits, plus the first packet bytes for exceptions. The pipe the IPA sent our ping to is therefore visible (a modem pipe 6–9/12/14 = good; dst 2 + exception = no route). a6l_diag also shows `suspend_info`. In ipa3, ipa_lan0 was DOWN (EP2 suspended, HOLB on), so these statuses were dropped. That is the `TX_SUSPEND`/`HOLB_DROP` bits in `irq_stts 0x00070380` (bits 16/17; 18 = BAM idle; 7–9 = uC queue flags). This is harmless but made them invisible. |
| Test tooling (task 2) | New static **`a6l-net`** (NDK r27c, 447 KB) with `addr`/`route` (ioctl, no ip binary), `ping` (**SOCK_RAW** ICMP bound with SO_BINDTODEVICE; the kernel treats an unrouted destination as on-link for a bound socket, so the Wi-Fi/USB routes are untouched), `dns` (UDP A query bound to the interface), `http` (TCP connect + HEAD /) and `stats`. run.sh also sets `ping_group_range` so toybox ping works as a fallback, disables IPv6 on the IPA/rmnet netdevs (IPV6=1 keeps it), brings ipa_lan0 UP, turns on `dump` for the test, and prints counters and pipe 2/4/5 **before/after**. |

```
rmnet_ipa0 rx 0 tx 3 rx_drop 0 tx_drop 3        <- tx = poll_tx completions; tx_drop = non-MAP (IPv6) on rmnet_ipa0

irq_stts 0x00070380 = uC q bits 7,8,9 | TX_SUSPEND 16 | TX_HOLB_DROP 17 | BAM_IDLE 18 (latched; irq_en = UC_IRQ_1 only)
```

In kmsg: no smmu fault and no BAM error; the uC and QMI handshake are complete. The only ipa2-lite `tx_dropped++` is in `ipa_ndev_start_xmit` (protocol ≠ ETH_P_MAP, linearize failure, or an enqueue error other than -EBUSY). A completion-path error cannot produce it.

## 5. Risks and unknowns
* The IPv6/no-traffic explanation of the ipa3 counters is solid, since it is derived from the code paths. It also means **the IPv4 data path is still completely untested**. The two fixes (route index 7, QMI acks) are downstream-conformance fixes: either one may or may not have been the blocker.
* The layout change moves the modem SRAM partitions by 8–16 bytes. They are all communicated over QMI (INIT_DRIVER), as before. If the modem rejects INIT_DRIVER (the `[ ] INIT_DRIVER response OK` box), fall back with `IPA_PARAMS="rt_apps_entry=0"`.
* The 0x24 decoder has mandatory TLVs. If the modem's 0x24 layout differs, the kernel logs "failed to decode incoming message" and sends no reply, which is the same as before.
* The ipa3 status line showed `[ ] INIT_DRIVER response OK` although kmsg had `A6L_IPA modem INIT_DRIVER response OK`: the run.sh pattern lacked the word "modem" (cosmetic), fixed in ipa4.
