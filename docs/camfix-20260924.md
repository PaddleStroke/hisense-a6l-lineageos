# camfix: why the cameras gave no frames, and the fix (camfix agent, 24 Sep 2026)

Status: **built and checked offline only (compiles cleanly, overlay merges, laptop copy 23/23 sha OK). Not run on the phone.**

The attended run on 24 Sep had three failures. All three have a concrete cause in the **mainline 7.2.3 code**, not in the sensor tables. Evidence: laptop `~/A6L-usb-20260915/v75/logs/klog-141643.txt`, relay outputs r204–r208.

## 1. Findings

| Symptom (attended) | Root cause | Fix |
|---|---|---|
| IMX576 STREAMON ok, then `VFE sof timeout` / `reg update timeout` / `halt timeout`. The media graph had **no msm_ispif** (csid → vfe0_rdi0 direct). | `camss.c camss_probe()` allocates `camss->ispif` only for `CAMSS_8x16/8x39/8x53/8x96`. **`CAMSS_660` is missing**, even though `ispif_res_660` exists and `camss-ispif.c` supports 660. The driver therefore builds the newer-SoC topology (CSID → VFE). On sdm660 the CSID output reaches the VFE **only through ISPIF**, so the VFE never sees SOF. | Patch 1: add `CAMSS_660` to the ISPIF allocation. The graph becomes csiphyN → csidM → **msm_ispifM** → msm_vfe0_rdi0. `a6l_camcap` already handles the ISPIF path. |
| (same) | `camss-csiphy.c` maps `csiphyN_clk_mux` (0xca00120/124/128, the CSIPHY → CSID select) under the same version list, also **without 660**. `base_clk_mux` = NULL, so the PHY is never steered to its CSID. | Patch 2: add `CAMSS_660` there as well. |
| S5K3T1: `Failed to power up pipeline: -22` (silent) | `run-camera.sh` used CSID2. `csid_set_power()` → `vfe_parent_dev_ops_get(camss, id)` returns `-EINVAL` when `id >= vfe_num` (sdm660: 4 CSIDs, 2 VFEs). Nothing is printed. The IMX576 failure did not cause it. | Patch 3: on ISPIF SoCs a CSID with no VFE of the same index is a no-op (`put` already was). The defaults also move to CSID0/1: imx576 → csid0, s5k3t1 → csid1, hi846 → csid0. |
| Hi-846: `this mode is not supported for 4 lanes` for every size | Upstream bug in `hi846_set_format()`: it checks the 4-lane table of the **current** mode before it picks the new mode. The default mode is 640x480, which has no 4-lane table, so every S_FMT fails on a 4-lane board. 4-lane modes: **1280x720@90 and 1632x1224@30** (640x480 is 2-lane only; there is no full-res 3264x2448 mode upstream). | Patch 4: `cur_mode` defaults to 1632x1224 when `nr_lanes == 4`, and requests are snapped to a 4-lane mode. `run-camera.sh` defaults to 1632x1224. |
| camss: `supply vdda/vdd_sec not found, using dummy` | The overlay lacked the CSID rails. Stock `qcom,csid@ca30x00` has `qcom,mipi-csi-vdd-supply` = **pm660_l1** (1.2 V, `qcom,csi-vdd-voltage` 1200000) and `vdd_sec-supply` = **pm660l_l1** (925 mV). The stock CSIPHY nodes only list the gdsc and smmu supplies. | Overlay: `&camss { vdda-supply = <&a6l_vreg_l1a>; vdd_sec-supply = <&vreg_l1b>; }`. Both labels and phandles (0xfb, 0x37) are checked in the merged v74 DTB. |
| Hi-846 `External clock freq should be 25000000, not 24000000` | Stock drives **all three MCLKs at 24 MHz** (`qcom,clock-rates = <0x16e3600>` in camera@0/1/2 and eeprom@0/1/2). Upstream Hi-846 tables assume 25 MHz. At 24 MHz every PLL output is 4 % lower (link ≈192 MHz, ≈28.8 fps). The warning is harmless. | No change. MCLK stays at 24 MHz. |

Other checks, with no change needed:
- **Lane order**: stock LaneAssign 0x4320 / LaneMask 0x1F means straight 4-lane wiring. `data-lanes = <0 1 2 3>` + `clock-lanes = <7>` on the camss side gives the 3ph-1.0 COMMON_CTRL5 value 0xd5 (lane mask 0x8f). This matches, as does `<1 2 3 4>` on the sensors.
- **Link frequencies vs register tables**:
  - IMX576 binned mode: OP PLL 24/4·340 = 2040 MHz, op_sys_div 4 → 510 Mbps/lane → 255 MHz. This is consistent with the menu.
  - S5K3T1: 282 MHz (564 Mbps/lane).
  - The PIXEL_RATE values were checked earlier (`hts·vts·fps`).
  - Settle count depends only weakly on link_freq: 255 vs 313.5 MHz shifts t_hs_settle by less than 3 ns.
- **Clock rates**:
  - Mainline picks the lowest level ≥ link/4. That gives a 100 MHz CSIPHY timer and settle_cnt = 3, and a 100 MHz CSID clock.
  - Stock uses a 269.33/310 MHz timer and a 310 MHz csi_src.
  - Patch 5 (module params `a6l_phy_fast`, `a6l_csid_fast`, both default 1): timer = 269.33 MHz (settle_cnt ≈ 20, stock-like) and CSID = 310 MHz. Set a param to 0 for upstream behaviour.
  - The VFE clock is unchanged: pixel·bpp/64 → 120/200 MHz.
- **Sensor start**:
  - Both drivers write init + mode tables. They contain no `0x0100` write, so standby holds until the end. Then controls, then `0x0100 = 1`.
  - camss calls sensor s_stream last, so the PHY is armed (LP-11) before HS starts.
  - The tables set CSI lane mode `0x0114 = 3` (4 lanes) and RAW10 (`0x0112 = 0x0a0a`).
- **Power after a failed stream**: the sensors use runtime PM with a 1 s autosuspend. Their `enable_streams` error path puts the reference, and every stream-on re-runs the full reset + init. The S5K3T1 -22 was camss (CSID2), not the sensor. `MODE=off` rmmods the sensor drivers, which powers down gpio51.

New debug (proves whether the sensor transmits, independently of CAMSS):
- `imx576_a6l`/`s5k3t1` read the CCS `FRAME_COUNT` (0x0005) before and 200 ms after `0x0100 = 1`, and again at stream-off. They log `A6L_SNS_FC <w>x<h> mode_select=0x1 frame_count a -> b in 200 ms: SENSOR_STREAMING|SENSOR_NOT_COUNTING` and `A6L_SNS_FC_STOP frame_count N`. Module param `dbg_fc=0` disables this.
- camss logs `A6L_CSIPHY<n> link_freq … timer … settle_cnt … lanes 4 mask 0x8f csid <m>` and `A6L_CSID<m> csi<m> rate …` on every stream-on.

## 3. Attended test (ATTENDED ONLY)

Before starting:
- Needs Pierre's go: this turns on the camera 2.8 V rail, the MCLKs **and the CSID rails pm660_l1 (1.2 V) / pm660l_l1 (≤0.925 V)**, which are stock camera rails.
- No RF, no flash writes.
- **Fresh V74 recovery boot**: the old `qcom-camss.ko` must not already be loaded. If it is, reboot.

From the laptop shell in `~/A6L-usb-20260915`:
```
adb -s HLTE730T-PROBE shell 'export PATH=/tmp/bin:$PATH; rm -rf /tmp/camera2'
adb -s HLTE730T-PROBE push v75/camera2 /tmp/camera2
adb -s HLTE730T-PROBE shell 'export PATH=/tmp/bin:$PATH; D=/tmp/camera2 MODE=probe sh /tmp/camera2/run-camera.sh'
```
The probe run should print:
- `SHA_PASS 23 files`
- `IMX576_PROBE_PASS`, `S5K3T1_PROBE_PASS`, `HI846_PROBE_PASS`, `GT9769_PROBE_PASS`
- `CSID_RAILS_PASS` (no "supply vdda not found")
- `ISPIF_IN_GRAPH_PASS`

Then run the capture tests, one per sensor. No optics are needed for bars.
```
adb -s HLTE730T-PROBE shell 'export PATH=/tmp/bin:$PATH; D=/tmp/camera2 MODE=bars SENSOR=imx576 sh /tmp/camera2/run-camera.sh'
adb -s HLTE730T-PROBE shell 'export PATH=/tmp/bin:$PATH; D=/tmp/camera2 MODE=bars SENSOR=s5k3t1 sh /tmp/camera2/run-camera.sh'
adb -s HLTE730T-PROBE shell 'export PATH=/tmp/bin:$PATH; D=/tmp/camera2 MODE=bars SENSOR=hi846  sh /tmp/camera2/run-camera.sh'
```
Expected for each sensor:
- `linked msm_csidM:1 -> msm_ispifM:0` and `msm_ispifM:1 -> msm_vfe0_rdi0:0`.
- `A6L_CSIPHYn link_freq 255000000 timer 269333333 settle_cnt ~20 lanes 4 mask 0x8f`. The link_freq is 282000000 for S5K3T1 and 200000000 for Hi-846.
- `A6L_SNS_FC … SENSOR_STREAMING`. Hi-846 has no FC log.
- `frame 0..4 seq …` and `CAPTURE_<sensor>_bars_PASS`.
- Then `adb pull /tmp/cam-<sensor>-bars.raw` and `python3 v75/camera2/raw10_to_png.py …`. The script prints the exact command. The PNG should show colour bars.

Then:
- `MODE=live` for each sensor (point at a lit scene; tune `EXP`/`GAIN`).
- `MODE=focus`: Pierre listens for the VCM.
- `MODE=off` to finish.

How to read failures:
- `SENSOR_NOT_COUNTING` means the sensor is not streaming: a sensor table, reset or MCLK problem. CAMSS is not at fault.
- `SENSOR_STREAMING` but still `VFE sof timeout` means a receive-side problem. Retry with `insmod qcom-camss.ko a6l_phy_fast=0 a6l_csid_fast=0` (upstream clocks) after a reboot. For IMX576, also try `CSID=1`. Send dmesg lines `A6L_CSIPHY`, `A6L_CSID` and `ispif`.
- `Failed to power up pipeline` with no other line means an old camss is loaded: reboot fresh.

## 4. Risks / unknowns
- The fix is inferred from source; a compile does not prove it works on hardware. The ISPIF path for 660 is upstream code, but it is unexercised on this kernel.
- The pm660l_l1 constraint in the base DT is 0.8–0.925 V and camss never calls set_voltage. The rail therefore runs at whatever RPM or the regulator core chooses (it is probably already on for other consumers). If CSID misbehaves, pin it to 925 mV in the ROM DT.
- CSID at 310 MHz and the PHY timer at 269 MHz match stock, but mainline sdm660 has no MMCX corner voting for camss. If something is unstable, set the params to 0.
- The IMX576 5760x4312 mode (2 Gbps/lane) is still untried. Test only after 2880x2156 works.
