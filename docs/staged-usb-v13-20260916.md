# V13: separate USB binding from serial output

The V12 photograph proves RAM PID 1 ran, mounted virtual filesystems and
successfully returned from USB gadget setup at about 5.39 seconds. The host
captured no diagnostic USB enumeration. The display subsequently went black.
Neither that photograph nor the host capture proves a kernel panic or poweroff.

V13 changes only the diagnostic RAM program. Kernel, device tree, regulator
constraints, disabled eMMC and boot arguments remain identical to V12.

The stages are measured with CLOCK_MONOTONIC relative to the diagnostic loop:

| Stage | What happens | Useful observation |
| --- | --- | --- |
| 0–20 seconds | Collect logs in RAM, heartbeat every 2 seconds; no gadget configured | Failure here precedes gadget binding |
| At 20 seconds | Configure ACM, print before/after UDC bind | A missing end marker narrows the last observed operation |
| 20–40 seconds | Heartbeats and read-only UDC state/speed/runtime status | Host enumeration can occur without opening ttyGS0 |
| At 40 seconds | Print before/after serial open and first write | Distinguishes binding from serial I/O |
| Thereafter | Send bounded 16 KiB chunks; heartbeats and UDC status | Collect actual kernel logs if the host sees USB |

Serial open is attempted once after successful gadget setup. Fatal serial write
errors are reported before close; the trial does not reopen repeatedly. Deferred
device snapshots remain bounded. Kernel log replay goes only to the RAM journal,
never back into `/dev/kmsg`. There are no block-device opens or persistent mounts.

The kernel's `gs_open()` was inspected locally: it uses locks and can start USB
I/O when connected. O_NONBLOCK is not evidence that all driver operations are
nonblocking. This is a reason to instrument the boundary, not a demonstrated cause.

An intact screen with advancing heartbeat proves diagnostic userspace remains
scheduled. A frozen/black screen alone does not establish a dead CPU; USB host
observations and later boot information must be considered together.

Validation and physical state are recorded in the V13 artifact/capture reports
and the current entry in `resume-next-session.md`. QEMU cannot emulate the A6L's
Qualcomm USB controller or validate physical enumeration.

## Physical result and cleanup

The confirmed Recovery selection at09:58:20UTC produced RAM heartbeats through
seconds18 (kernel23.010655), with USB/serial attempt counters still zero. No
USB-start marker is visible in the last video frame. Short-lived subsequent
messages could be absent from the recording; this does not prove a pre-bind
crash. The awake laptop captured no diagnostic USB enumeration.

Stock recovery was restored with full readback at10:05:38UTC. All twelve desktop
readbacks passed; original Android returned at10:06:01UTC. Host services and
temporary sleep inhibition were cleaned up. The user saw Android return directly,
not the stock recovery menu. BCB was bootonce-bootloader during restore readback;
its post-restart contents are unverified. Retain the next installer zero-BCB guard.

Next useful test: a longer idle control, then separate gadget configuration, UDC
binding and serial open, with visible pauses before each operation. Keep the
existing kernel/DT/voltage constraints unchanged while localizing the failure.
