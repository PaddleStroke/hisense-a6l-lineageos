Readings (new):
1. **What 0xC94 is.** It is the VFE 4.8 per-WM **bus error status** (bit n = WM n), and s1 bit4 is its summary bit.
   - Stock `msm_vfe48_get_bus_err_mask` (ELF `ffffff80088d0fcc`) reads 0xC94 and clears the bits in the software
     `bus_err_ign_mask` (`vfe_dev+0x5c8`). If nothing is left, it clears s1 bit4.
   - Stock `msm_vfe47_get_overflow_mask` = 0x09fffe7e includes s1 bit4, so a surviving bit → halt + recovery.
   - **s1 bits 9..15 (image-master UB overflow) were never raised in any t27–t29 run.** So this is an error reported on
     the AXI write side, not a UB overflow (camfix5's "UB overflow" wording was wrong).
   - UB depth made no difference (ub192/682/1904 all fail at the same point), which agrees.
2. **The WM stops dead after the first error.** It does not keep overflowing; it produces one error at SOF 2–5, no second one, and no done.
   The probe's ≤ 17 lines/frame are the tail of that stall.
3. **VBIF.** The camfix6 VBIF writes did **not** stick: the START readback after `a6l_vbif_apply` still shows `wgather(ac) 0`
   and `outrd(d0) 0x10`. VBIF `pnderr/srcerr` are 0, so the VBIF saw no error response. In practice VBIF QoS has never been applied.
4. **`A6L_AXI ~0 kHz` was a decode bug, not a dead clock.**
   - cfg 0x203 = source 2 = **MMPLL4** (L=0x28 → 768 MHz), HID 3 = ÷2, so the MMSS AXI runs at **384 MHz**.
   - It is unchanged by the 2/4 or 6/8 GB/s votes (stock's maximum is 406 MHz).
   - The AXI clock is not the limit. camfix7 fixes the decode.
5. `imgsize0=0` is **stock-identical**. Stock `msm_vfe47_axi_cfg_wm_reg` in frame-based mode writes only ADDR_CFG,
   BUFFER_CFG (= ADDR_CFG value) and +0x28 = 0xffffffff, and never writes IMAGE_SIZE.
6. No "Unhandled context fault" or global fault appears in any log. Nobody has read the SMMU fault registers, though, so a fault whose IRQ is
   lost, or a TBU-level stall, is not excluded.

## 3. Hypotheses, ranked
1. **SMMU/TBU side (strongest).**
   - What it is: the first frame's writes run into the SMMU. Either a translation fault whose context IRQ is never handled
     (terminate → AXI SLVERR → 0xC94), or a TBU/micro-TLB configuration that mainline leaves at reset (impl-defs, ACTLR).
   - What distinguishes it: an error response rather than overflow; the start-of-stream timing; independence from the clock and the UB.
   - Test: `a6l_v7` bit0 reads FSR/FAR/FSYNR at the first bus error. Bits 1/8 apply the stock impl-defs and ACTLR.
2. **Line-rate / latency limit.**
   - The input is ~255 MB/s while a line is active: 3600 B / 14.1 µs of a 15.05 µs line.
   - `HTS=11088/22176` halves or quarters the line rate with the same MIPI timing and frame. If hts2 or hts4 pass, it is bandwidth/latency.
     In that case repeat with iccmax and then the SMMU bits.
3. **NoC/SMMU clocks gated** (mnoc_ahb, bimc_smmu_ahb/axi, or the BIMC SMMU GDSC). The `A6L_MMCC` line shows CLK_OFF and GDSC PWR_ON directly.
   Bit 4 holds the clocks for the whole stream.
4. **VBIF QoS never applied** (the write is lost). The readback stays in the log. It is low-ranked because VBIF reports no error.

Ruled out:
- VFE core clock (camfix5)
- UB depth, frame vs line WM, burst field, WM MAX (camfix4–6)
- "AXI ~0 kHz" (decode bug)
- `imgsize0=0` (stock-identical)

### PASS criteria
- Probe: `CAMSS_CAMFIX7_PASS`, `IMX576_HTS_PASS`, `V7_DEFAULT 1` and the 4 sensor `_PROBE_PASS`.
- Diagnostics present: `A6L_MMCC START cbcr …`, `A6L_MMCC … pll … mmpll4:… LOCK`, `A6L_SMMU START cb<N> sctlr …`.
  If the SMMU is unpowered, you get `A6L_SMMU … skipped: gdsc …` instead, which is itself a finding.
- Fix PASS for a sweep variant: in the table, done ≥ 0.9 × (sof − first), be 0, maxl/frame ≈ 2156 (the frame size is the same for every hts) and capture PASS.
  Then confirm on the normal path with the probe off:

### Reading the result
| observation | meaning / next |
|---|---|
| `A6L_SMMU BUSERR cbN … fsr` ≠ 0 (FAR inside ping/pong ff000000..fff66ec0) | an SMMU fault that nobody reported. Check the context IRQ mapping and the SCTLR CFIE/CFCFG, and the IOVA mapping or permission (FSYNR0 WNR/PNU). The fix goes in the SMMU/DT |
| `gfsr` ≠ 0 at BUSERR | unmatched stream ID: the VFE uses a SID outside 0xc00..3 → extend the iommus (overlay) |
| smmu or smmuall PASS, base FAIL | the stock SMMU impl-defs (and/or ACTLR) are needed: carry them into the ROM (arm-smmu-qcom impl for sdm630 mmss, or a camss init hook) |
| hts2/hts4 PASS, base FAIL | a bandwidth/latency limit. Compare with iccmax/clk*/smmu*, and check DBGFS (mmssnoc/bimc rates, bimc_smmu genpd) |
| clk/clkicc PASS | a NoC/SMMU branch was gated: add these clocks to the camss DT clocks (overlay) |
| MMCC shows `vbif_axi:OFF`, `smmu_axi:OFF`, `mmpll4 nolock` or bimc_smmu gdsc bit31 = 0 during streaming | that is the cause. Fix the provider (mmcc/genpd) |
| hi846 or s5k3t1 PASS while imx576 FAILs | the shared CAMSS path works. Look at the imx576 rate (hts result) |
| everything FAILs with FSR 0, GFSR 0 and all clocks on | the next step is the CSID test generator (the Astra review) and the MNOC ErrorLogger |

## 6. Risks
- The SMMU halt also pauses display DMA for microseconds; the impl-defs and ACTLR persist until reboot, which is why they come last in the sweep.
- The SMMU register reads are gated on BIMC SMMU GDSC PWR_ON and bimc_smmu_ahb running. An unclocked read would hang the bus (camfix3 lesson).
- The first-BUSERR dump runs in the VFE IRQ handler (MMIO reads + dev_info) and runs once per stream.
