Agent `data2`. All work was done offline: I never touched the phone and ran no adb. **Nothing here has run on hardware yet.** The bundle is `v75/ipa3`, staged on the laptop (`LAPTOP_STAGED_OK`).

## 1. Why INVALID_OPERATION (details)
* Our old request was libqmi-correct: TLVs 0x11 raw-ip, 0x12/0x13 QMAP (5), 0x15 32, 0x16 32768, 0x17 {4,1}. What was missing is the port mapping. On IPA targets the modem has no static data port for "embedded 1". The peripheral driver/netmgr creates it with DPM Open Port and passes the IPA pipe pair. On stock this is `netmgr_qmi_dpm_port_open` (retried for `dpm_retry_timeout` 10 s). Without that mapping, WDA and WDS bind report INVALID_OPERATION.
* Stock asks for **QMAPv3 (7)** in both directions (DL aggregation 10 packets/8192 bytes). QMAPv3 means QMAP plus MAPv4 checksum offload, which the stock rmnet_ipa provides on EP5. ipa2-lite has no checksum offload and our rmnet flags are 0x01, so the default stays **QMAP (5)**. The modem's grant is logged, as the ModemManager order QMAPv5 → v4 → QMAP does. Variant for the attended run: `export A6L_WDA_UL=7; export A6L_WDA_DL=7;`. With it, rmnet would need the checksum flags. Use it only if QMAP is refused.
* ipa2-lite does no EP5 aggregation. Single QMAP frames are what rmnet deaggregation expects anyway, and the DL max values only set what the modem may pack.
* WDS Bind Mux Data Port stays {4,1} with mux id 1… (unchanged). ril3's DSDS subscription bind is kept, because my edits were re-applied on top of ril3's concurrent changes.

## 3. ipa2_lite: the MODE=status reset
* Observed today: resets happened only when `a6l_diag` was read while the IPA was runtime-suspended. With `power/control=on` and no dump there was no reset.
* Runtime suspend only drops the RPM IPA clock to `clk_idle_hz` (9.6 MHz). The IPA ISR read `IPA_IRQ_STTS` at that rate during the handshake (uC INIT_COMPLETED) **without** a reset. So the fatal access was probably not the global registers. More likely it was the **pipe 6–14 BAM/EP registers** of the modem-owned pipes, which the old dump read; after the handshake those pipes can be XPU-protected, and an XPU violation is fatal on this unit (qfprom precedent). This is a hypothesis. **Both** causes are now covered: a PM reference, and the AP pipes only.
* `diag_pipes` (module parameter, 0644) can widen the dump (`DIAG_PIPES=0x7fff` in run.sh) for a deliberate experiment only. Do not use it in normal tests.
* Also seen in today's kmsg (not fixed here): `arm-smmu 16c0000.iommu: failed to request context IRQ 1 (25)`. Context faults on anoc2 are therefore not reported, so an IPA SMMU fault would be silent. Handover: flash/DT agent (anoc2 IRQ list in the V75 DT).

   (The load prints `diag | head -8`. That is now the safe dump: `A6L_IPA_DIAG pm active …` and pipes 2–5.)
2. **Pierre types ONE line (RF: radio + PIN + online + data):**
   `adb -s HLTE730T-PROBE shell 'export PATH=/tmp/bin:$PATH; export A6L_RF_APPROVED=1; export A6L_PIN=<PIN>; sh /tmp/ipa3/data-test.sh' 2>&1 | tee v75/logs/ipa3-data-$(date +%H%M).txt`
   It runs: radio2 (A6L_KEEP=1, 20 s watch) → PIN → `mode online` → waits ≤ 60 s for `reg=registered ps=1` → status (no dump) → **dataformat** → data (KEEP=30, ping DNS and 1.1.1.1 through /32 host routes, nslookup) → `mode lowpower`.
   **Expect:**
   * `A6L_QMI_DATAPATH dpm: open port hw ep=4/1 rx_ep(consumer)=4 tx_ep(producer)=5: ok`, then `wda: format set llp=2 ul=5 dl=5 …`, then `A6L_QMI_DATAFORMAT_PASS`;

3. **If it fails**, read the `A6L_QMI_DATAPATH` lines:
   * `dpm … INVALID_ARG` or `MISSING_ARG`: retry with the pipes swapped: `export A6L_DPM_RX_EP=5; export A6L_DPM_TX_EP=4;` and `export SKIP_RADIO=1;` (the modem is already up).
   * `dpm: service 0x2f not found`: run `a6l-qmi lookup` and check that DPM(47) is listed.
   * DPM ok but WDA still INVALID_OPERATION: try `export A6L_WDA_UL=7; export A6L_WDA_DL=7;`, then `A6L_WDA_DL=0` (no DL aggregation).
   * Data up but no ping: keep the output. The rmnet_ipa0 tx/rx counters and the pipe 4/5 rd/wr in the (safe) dump are printed.
4. Finish: `sh /tmp/ipa3/ril-test.sh stop` or reboot. Never `rmmod ipa2_lite`.

## 7. Risks and unknowns
* Nothing has run on the phone. The DPM fix rests on the stock config, netmgrd strings, downstream rmnet_ipa and ModemManager's IPA path, not on a capture of the SDM660 modem's reply.
* The DPM field order (rx = 4, tx = 5) follows MM, libqmi and downstream. If the modem wants the reverse, the §5.3 swap covers it.
* It is not known whether the modem closes the DPM port when the client goes away. The manager keeps the DPM client for its lifetime. The CLI `dataformat` exits and closes it; `data` re-opens it (NO_EFFECT is accepted).
* The XPU-on-modem-pipes explanation of the reset is inference; both the PM reference and the pipe mask are in place.
* The data path past the call (ping) is still untested on SDM660 ipa2-lite (see docs/ipa-20260924.md §6).
* ril3 was editing the same radio files at the same time. My changes were re-applied with anchored edits on top of ril3's 11:2x UTC version, and the host tests were re-run on the merged tree (165/165). If ril3 later overwrites these files from an older copy, the DPM change is lost: check `grep openDpmPort radio/qmi/src/datacall.cc`.
