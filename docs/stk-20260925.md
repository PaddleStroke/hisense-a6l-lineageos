# Front light/proximity sensor STK3338 — agent `stk`, 25 Sep 2026 (offline only)

**Status:** root cause analysed from the stock DT + stock kernel disassembly; driver, overlays, test tools, Android HAL
built and checked offline. **Nothing ran on the phone.** Tests T1 (read-only probe) and T2 (data) are ready.

## 1. Why it never answered (findings)
Stock DT `stock-00.dts:9323` (same in stock-01): `i2c@c1b6000` (blsp_i2c6, gpio22/23, same pins as mainline),
`stk-stk3338@47`, `compatible = "stk,stk3x3x"`, IRQ gpio71 falling (pinctrl `stk3338_int_pin`: pull-up, 6 mA),
**vdd = pm660l_l3** (phandle 0x191), **vio = pm660_l13** (0x17b), no enable/LDO GPIO. Bus neighbours: a96t346 SAR
@0x20 (vdd L3, vio L13), tfa98xx @0x34 (vdd L13), nfc @0x28 (disabled). Stock sensor list: `proximity_extend_front_1`
(Sensortek, flags 0x3 = **wake-up**, on-change) and `light_extend_front_1`; rear ams TMD3702 = `*_extend_back_1`.

Stock driver `stk3x3x` v3.11.0 (`stk3x3x_probe` @ffffff8008c0921c, `stock-symbolized.elf`), power-on/probe:
1. `regulator_get("vdd")` → `set_voltage(2 800 000, 2 950 000)`; `regulator_get("vio")` → `set_voltage(1 750 000,
   1 950 000)`; enable vdd, enable vio, **msleep(3)**.
2. `stk3x3x_check_pid`: **ignores the DT address**, loops over a table at `stk_ps_driver+0x308` = **{0x67, 0x47}**,
   sets `client->addr` and reads 2 bytes at 0x3E (PID, RID). First success wins; PID must be ≠ 0
   ("PID=0x0, please make sure the chip is stk3x3x!"). So the stock chip may well sit at **0x67**.
3. `software_reset`: write 0x05 = 0x7F, read back, write 0x80 = 0, usleep 13–15 ms.
4. `init_all_reg`: 0x00 STATE=0x08, 0x01 PSCTRL=0x71, 0x02 ALSCTRL=0x21, 0x03 LEDCTRL=0x40, 0x05 WAIT=0x20,
   0x04 INT=0x01, **0x4E=0x20, 0xFA=0x01**, PS thresholds 0x06/0x08 = 0x78/0x37. Data: FLAG 0x10, PS 0x11, ALS 0x13
   (+0x17/0x19/0x1B extra channels). → **Register map = mainline stk3310 family** (same STATE/PSCTRL/ALSCTRL/INT/
   THD/FLAG/PS/ALS/ID 0x3E layout).

Our side (V74 DT `recovery-v74-candidate-20260923/merged-captured-abl.dtb`): candidate S1 `light-sensor@47`
(`sensortek,stk3335`, vdd = L3 fixed **3.0 V** but **not always-on**, no vio), L13 always-on (1.78–1.95 V). The only
other L3 consumer is the rear touch (`edt-ft5406` vcc). **Mainline stk3310.c has no regulator code at all**, so
under V71/V74 nothing enabled L3 unless the rear-touch driver happened to be loaded; "pinned to 3.0 V" (V71) only set
the voltage. Ranked causes: **(1) vdd (pm660l L3) off** — no consumer enabled it; **(2) wrong address: stock tries
0x67 before 0x47**; (3) chip ID: harmless — mainline only logs unknown IDs (STK3338 PID not in its table; stock only
needs PID ≠ 0). Not a shared-bus issue (TMD3702 is on c176000; touch on c1b5000). No LED supply in the DT (LEDA is
presumably on VPH/VBAT). Bus health itself under our kernel is unproven (nothing on c1b6000 ever answered) — T1
reads the a96t346 @0x20 as a reference.

- **T1 probe (read-only):** prints the c1b6000 adapter, the L3/L13 regulator lines, then PID reads at 0x47, 0x67 and
  0x20 **before** and **after** `a6l_stk_ovl.ko`. Pass = `OK 0x47 reg 0x3e: <pid> <rid>` or `OK 0x67 …` (pid ≠ 00).
  Reading: NAK before + OK after → cause (1) (L3 off). OK only at 0x67 → cause (2): put `reg = <0x67>` in the V75 DT.
  0x20 also NAKs after the vote → bus/pinctrl problem (check `i2c-qup` probe in dmesg, gpio22/23 function).
- **T2 data:** insmod `stk3338_a6l.ko`; dmesg `A6L_STK found at 0x.. PID=0x.. RID=0x..`; 30 samples of
  `prox/light/irqs`; **cover the top edge next to the earpiece at "COVER", uncover at "UNCOVER"**, then point at a lamp.
  Pass = prox rises well above 120 when covered and falls when uncovered; `A6L_STK_EVENT … NEAR` / `FAR` lines; irq
  count increases; light changes with the lamp/palm. If prox never crosses 120: re-run with
  `STK_ARGS='ps_thd_high=<covered-10%> ps_thd_low=<uncovered+10%>'`. `rmmod stk3338_a6l` and `rmmod a6l_stk_ovl`
  undo it.

## 4. Android (sensors HAL)
- The trout IIO sub-HAL (hals doc) only handles buffered accel/gyro, so light/proximity get their own module:
  `device/hisense/a6l/hals/sensors/stk3338/sensors_a6l.c` → **`sensors.a6l.so`**, a legacy sensors HAL (API 1.3)
  loaded by LineageOS' `android.hardware.sensors@2.0-subhal-impl-1.0` (hardware/lineage/interfaces/sensors) inside
  the multihal. Handle 1 = **"STK3338 Proximity (front)", WAKE-UP + on-change**, 0 cm near / 5 cm far, from IIO
  events (initial state from `in_proximity_raw` vs the rising threshold on activate); handle 2 = "STK3338 Light
  (front)", on-change, lux = raw × scale polled every 200 ms while active; flush → META_DATA_FLUSH_COMPLETE.
- **The rear TMD3702 is deliberately not exposed as proximity**, so Android's default (wake-up) proximity sensor —
  the one PowerManager uses for the in-call screen-off — is the front STK3338. If the rear sensors are added later,
  use vendor string types, never TYPE_PROXIMITY with the wake-up flag.
- Checked: NDK clang build of `sensors.a6l.so` against the Lineage tree headers (libhardware/liblog/libcutils/
  libsystem) with -Wall -Werror: HAL_NDK_BUILD_PASS, exports HMI (relay stk-09). **Not built with m, never run.**
- Permissions: `/dev/iio:device*` 0660 system (already in `hals/rootdir/etc/ueventd.a6l-hals.rc`), sysfs attrs are
  world-readable. SELinux: hal_sensors_default needs `iio_device` chr_file read/ioctl + sysfs read (permissive now).

## 6. Unknowns / risks
- Which address (0x47 / 0x67) and whether L3-off was the whole story: only T1 answers that.
- STK3338 PID value unknown (logged at probe). 0x4E/0xFA are undocumented stock tuning writes, copied as is.
- LEDCTRL 0x40 (stock) sets the IR LED current; if prox is flat, try `reg_ledctrl=0xff` (upstream chip default).
- Shared L3: rear touch and the a96t346 SAR sit on the same rail; the vote keeps it at the DT's 3.0 V (stock asked
  2.80–2.95 V; STK3338 range 1.7–3.6 V).
- The HAL was not run; proximity/flush/wakelock behaviour needs the ROM test (step 5.4).
