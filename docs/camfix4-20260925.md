## 1. What t25c shows
- Sensor streams, and RDI0 SOF arrives on every frame (238 in 5.5 s).
- The reg-update ack arrives once, at the first SOF (s0b5:1). The IRQ mask `0x80000120/0x20000380` has WM0 done enabled.
- BUS_CFG is 0x101, XBAR is 0xc00, and RDI0_CFG is 0x7. WM0 is enabled through 0xCEC (the 4.8 path, identical to stock `msm_vfe48_axi_enable_wm`).
- ping `ff800000`, pong `ff000000`. ADDR_CFG is 0x2 (frame-based, period 1), pattern is 1, IRQ subsample is 0xffffffff, and UB is 0/682.
  All of these match stock.
- **WM0 done: 0.** **Bus error s1 bit4 with 0xC94 = 0x1 (WM0)** arrives at the 2nd SOF, which means during the first frame
  the WM tried to write. t25b showed the same bus error at the same moment.
- **0x0a8 = 0x0b0 = 0 in both dumps.**

## 2. Root cause: the WM "max address" registers are never programmed
Stock `msm_vfe47_update_ping_pong_addr` (used by vfe48, disassembled at `ffffff80088d1c8c`) writes **two** registers per slot.
```
addr reg = 0xA0 + 0x2C*wm + (pingpong_bit ? 0x4 : 0xC)         (PING 0xA4 / PONG 0xAC)
max  reg = addr reg + 4                                        (PING_MAX 0xA8 / PONG_MAX 0xB0)
max      = (paddr + buf_size) & 0xFFFFFFE0,   buf_size = word_per_line*8*scan_lines (= frame bytes)
```
Upstream `camss-vfe-4-8.c` writes only the addresses. The MAX registers keep their reset value 0, so the first burst
of every frame is above "max". That produces the WM0 bus error (0xC94 bit0), the frame is never completed, and no
ping-pong done follows. This matches the t25c data exactly. In t25b, 2 dones slipped through in ~370 frames; the
framedrop explanation in camfix3 was wrong.

The public xiaomi/LineageOS msm-4.4 copy has `paddr32_max = 0`, which is why the camfix3 comparison missed this. The Hisense
kernel that ships on this phone computes the real value.

Second stock difference, also confirmed in the ELF: `msm_isp_axi_update_cgc_override(START)` sets bit `wm` in **VFE 0x3C**
(the bus WM clock-gating override) for every stream, and clears it at STOP. Upstream 4.8 `vfe_set_cgc_override` is empty.

Everything else checked against stock is identical: framedrop ((period-1)<<2, pattern at +0x24), RDI_CFG, IRQ mask
bits wm+8 / wm+9, enable via 0xCEC, frame-based ADDR_CFG and BUFFER_CFG (= ADDR_CFG value). The stock start order is
cfg_wm_reg → ping/pong (+max) → irq mask → enable_wm → reg_update → reload (0x80) → cfg_ub.

## 3. Changes: `device/hisense/a6l/kernel/camera/patches/camfix4_patch.py` (applied after camfix, camfix2, camfix3)
Cumulative diff vs 7.2.3: `patches/camss-sdm660-camfix4-cumulative.patch` (964 lines).
Build script: `device/hisense/a6l/camera/tools/build-camfix4.sh` (build dir `/home/a6l/camfix4`, `src-snapshot/`).
1. **Fix: `wm_set_ping/pong_addr` also write MAX = (addr + size) & ~0x1f**, clamped below 4 GiB.
   - The size is set per WM from the line's sizeimage at STREAMON. Only RDI lines get it; PIX keeps 0.
   - Param `a6l_wmmax` (default 1; 0 restores the old behaviour for A/B testing).
2. **Fix: CGC override (0x3C bit wm)** at WM enable and cleared at disable. Param `a6l_cgc` (default 1).
3. **`a6l_wm=4`: the simplest possible path**:
   - Two driver-owned ping/pong buffers, each 2x the frame size and filled with 0xA5A5A5A5, programmed once.
   - Frame-based, period 1 / pattern 1, IRQ on every frame. No drop logic, no address change and no reg-update on done.
   - Each done copies the finished slot into the next queued user buffer from a workqueue, with a cache clean, so camcap
     still gets frames.
   - At stream-off, `A6L_WM4_SCAN slot s done N written_words W first F end E frame S buf B head …` shows whether and
     how much the WM wrote. `end` beyond `frame` means an overrun, and 0 means the WM never wrote.
   - Variants:
     - `+2`: stock BUFFER_CFG.
     - `+8`: reload the WM on a bus-error IRQ (recovery experiment, any mode).
     - `+16`: in mode 4, program max = frame size instead of the 2x buffer.
4. `A6L_WM<n>_START` line after enable: 0x3C, WR_CFG, ping/max/pong/max, ADDR_CFG, UB, IMAGE_SIZE, BUFFER_CFG, pattern, subsample.
5. The default stays `a6l_wm=3` (stock-like every frame + scratch, now with max + CGC). This is the ROM candidate.

`run-camera.sh`:
- Knobs `WMMAX=`, `CGC=`.
- Probe marker `CAMSS_CAMFIX4_PASS`.
- New summary lines `WMSTART`, `WM4 …SCAN`, `DONES`.
- New **`MODE=wmloop`**: one bars capture per entry of `WMS` (default `"4 3 0 4:0:1 4:1:0"` = `WM[:WMMAX[:CGC]]`) in one boot.
  Outputs go to `/tmp/cam-<sensor>-bars-wm<W>-m<M>-c<C>.{raw,dmesg,log,out}`, with a summary in `/tmp/cam-<sensor>-wmloop.sum`.
  The params are reset to the defaults at the end.

## 6. Risks / unknowns
- **Not verified on HW.** The cause is inferred from the stock disassembly plus the register dumps (MAX = 0 in both runs, a WM0 bus error on
  the first frame in both runs). Whether max is inclusive or exclusive is taken verbatim from stock. Bit 16 (`WM=20`) tests a
  tighter max.
- Mode 4 allocates 2 × 15.5 MB (IMX576) of IOMMU-mapped, uncached memory. It is kept until rmmod (debug-grade). Copying and scanning
  through the uncached mapping is slow, around 50 ms per frame, so camcap receives every 2nd–3rd frame.
- The copy work only runs when a user buffer is pending. Frames may tear, because the WM keeps writing the same fixed slots.
- VBIF QoS (0xca40000: 0x124=3, 0xac=0x40, 0xd0=0x1010) is still not applied. It is not expected to matter.
