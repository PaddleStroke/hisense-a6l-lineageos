## 1. SMS: bare TPDU from WMS + `dtmf` / `call-list`

**Root cause.** The modem's WMS event report (TLV 0x11, format 6 GW_PP, transfer-only route) carries the TPDU
**without** the SMSC length prefix (real captures `040B9133…`). `sms::parseDeliver` read 0x04 as an SMSC length.
The HAL passed the same bytes to Android `newSms()`, which also expects SMSC+TPDU. So **the ROM would have mis-decoded every
incoming SMS too**, not only the CLI.

**Fix** (`device/hisense/a6l/radio`):
- `qmi/include/a6lqmi/sms.h`, `qmi/src/sms.cc`: `parseDeliver(pdu, SmscForm::Auto|Prefixed|Bare, &detected)`.
  Auto first tries a *strict* parse of both forms and keeps the first that matches: SMSC len ≤ 11 with a TOA high bit,
  OA len ≤ 20 with a TOA high bit, and the exact UD length for the DCS (GSM7 septets→octets, 8-bit/UCS2 octets).
  A status report must have ≥ 15 trailing octets. If neither strict parse matches, it falls back to lenient parsing.
  New helpers: `detectForm()` and `toSmscPrefixed()` (prepends `00` to a bare TPDU and is idempotent).
- `hal/ModemCore.cpp`: both MT paths (transfer route and stored+read) now call `::a6l::sms::toSmscPrefixed()` before
  `isStatusReport()`/`newSms()`. Android gets `00`+TPDU (SMSC unknown), which GsmSmsMessage accepts.
- `tests/qmi_tests.cc`: both real captures ("A6L loop test", "A6L test 1", from +33663336228, ts 260924144844), the
  classic prefixed vector, the same TPDU with an Orange SMSC prefix, `00`-prefixed round trip, a bare status report and
  garbage input. **Host tests: 131 passed, 0 failed** (gcc ASan/UBSan, WSL and Cowork VM).
- `tools/a6l_qmi_cli.cc`: `A6L_QMI_SMS_RX … form=bare-tpdu|smsc-prefixed fmt=N`. On a parse failure it now prints
  `A6L_QMI_SMS_UNPARSED`. New commands:
  - `call-list`: id, state, direction, type, mode, multiparty and number for every modem call.
  - `dtmf <digits> [wait_s]`: waits up to wait_s (30) for a call in CONVERSATION. Then, per digit,
    START_CONT_DTMF → 250 ms → STOP_CONT_DTMF → 150 ms. This is the same as Android start/stopDtmf.
    `A6L_DTMF_MODE=burst` uses BURST_DTMF (CDMA style; may be rejected on LTE/GSM). `A6L_DTMF_ON_MS`/`OFF_MS` tune timing.
    Digits allowed: 0-9 * # A-D. The command ends with `A6L_QMI_DTMF_PASS|FAIL`.
- `tools/ril-test.sh`: new steps `call-list`, `dtmf <digits> [wait]` (run in a 2nd shell during `dial`/`call-wait`), and
  `dial-dtmf <num> <digits> [s]` (RF: dial in the background, DTMF once answered, hang up after s).

## 2. GNSS: XTRA, coarse position, quiet NMEA log, HAL PSDS

**Library** (`device/hisense/a6l/gnss/lib`):
- `loc_v02`: `INJECT_PREDICTED_ORBITS_DATA` 0x0035. TLVs: 0x01 total size, 0x02 total parts, 0x03 part number
  (1-based), 0x04 u16 length + ≤ 1024 bytes, optional 0x10 formatType = 0 (XTRA).
  Also `GET_PREDICTED_ORBITS_DATA_SOURCE` 0x0036 (max file/part size + server URLs) and `…_VALIDITY` 0x0037
  (start GPS s + duration h), and `makeInjectCoarsePosition()` (INJECT_POSITION + horReliability LOW + positionSrc 0x1D).
- `GnssEngine::injectXtra()`: part by part. After each part it waits for the part's 0x0035 indication (status 0),
  like the Qualcomm loc client. If part 1 is rejected, it retries once without formatType. It then queries validity.
  `queryXtra()` and `injectCoarseLocation()` are also added. `REG_EVENTS` now includes INJECT_ORBITS_REQ.
  Indications for INJECT_UTC_TIME/POSITION are logged with their status.
- Fixed a TSan race: `serviceUp()` read `client_` while the worker replaced it (`clientMu_`).
- Host tests: **103 pass (ASan/UBSan)**. New `testXtra` covers the wire format, 3-part injection against the fake
  modem, source/validity parsing, and a failing part stopping the injection.

**CLI** `a6l_gnss_test` new options:
- `--xtra FILE [--xtra-part N] [--xtra-required]`

## 3. Haptics (PM660 LRA)

Stock (`qcom,haptic@c000`, qpnp-haptic) compared with our module:
- Actuator: LRA (0x4C=00 ✔).
- Play mode: direct / VMAX source (0x4E=00 ✔).
- Wave shape: square (0x4D=01 ✔).
- vmax: 3200 mV (0x51=0x38 → 3248 mV ✔).
- ilim: **800 mA** in stock; ours was **400**, because the V74 DT has no `qcom,ilim-ma` and the module defaulted to 400.
- SC debounce: **8 cycles** in stock (encoded 1). Ours wrote `32 & 0x7 = 0` = **no debounce**, a real bug that can cause
  false short-circuit shutdowns.
- Internal PWM: 505 kHz in stock. Ours never wrote 0x56/0x58.
- Auto-resonance: stock uses QWD plus `correct-lra-drive-freq`. PM660 auto-res enable is AUTO_RES_CTRL **0x4B bit7**,
  set about 20 ms after PLAY. Ours was always off, so the LRA was driven open-loop at the DT's nominal 150 Hz with an
  untrimmed clock. An LRA driven off-resonance gives almost no motion, which is the prime suspect.
- The 0x46=00 reading **after** the pulse is expected (the driver disables the module at stop). That is why
  snapshots DURING play are needed.

`a6l_pm660_haptics.c` changes (source under `device/hisense/a6l/kernel/a6l-pm660-haptics/`):
- ilim default 800 (DT or `ilim_ma=`). SC debounce encoding fixed (`sc_deb_cycles=8`). INT_PWM + PWM_CAP = 505 kHz
  (`int_pwm_khz=`).
- `pm660_autores` (0644, default 0): clears 0x4B bit7 before PLAY and sets it 20 ms after.
- SC events are counted and logged (`A6L_HAP short-circuit flag …`).
- New debugfs **`a6l_haptics/test`**: `echo "pulse <ms> <mv> [rate_us] [autores] [erm]"`. It runs one synchronous,
  bounded pulse and logs `A6L_HAP before/during/after t=… sc=…` snapshots of 0A (status: busy/SC/auto-res error),
  0B/0C (auto-res period readback), 46, 48, 4B, 4C, 51, 52, 53, 54, 55 and 70. It restores the registers afterwards.
- Bounds: ms 10..1000, mv ≤ 3200 (stock), rate 3000..10000 µs, ERM only ≤ 100 ms and ≤ 2 V.

`run-rest2.sh MODE=haptics` runs these pulses, asking Pierre after each one:
1. DT rate without auto-res.
2. With auto-res.
3. A resonance sweep at 170, 200 and 230 Hz.
4. Optionally (`HAP_ERM=1`) a 100 ms 2 V ERM click that proves the output stage.
5. The input-FF path with auto-res on.

What to read from the klog:
- 0x0A bit3 set → short circuit. Try `HAP_ARGS="ilim_ma=400"`, and check for a physical actuator fault.
- 0B/0C non-zero with auto-res → the LRA is connected and resonating. The period gives the true resonance
  (set `qcom,wave-play-rate-us` to it).
- 46 must read 0x80 and 70 must read 0x80 during play.

## 4. Hall sensor

`device/hisense/a6l/kernel/a6l-hall-v75.dtso` (updated):
- gpio-keys SW_LID on gpio75, GPIO_ACTIVE_LOW, pull-up pinctrl, 15 ms debounce, wakeup.
- gpio-keys has no supply property, so there is a new always-on `regulator-fixed` "a6l_hall_vdd_1p8" with
  `vin-supply = <&a6l_vreg_l13a>` (pm660 L13). The regulator core enables the supply of an always-on regulator, so this
  is an explicit, permanent L13 vote for the ROM.

`device/hisense/a6l/kernel/hall/ovl/a6l_hall_ovl.c`: runtime overlay module, the same approach as a6l_cam_ovl, for the V74 test.

**Offline check (misc-05/misc-07):**
- dtc builds the overlay, and it merges (`fdtoverlay`) onto the V75-on-V74 base
  (`firmware/extracted/ipa-20260924/m-a6l-ipa-v75-on-v74.dtb`): HALL_MERGE_PASS.
- In that base, `a6l_vreg_l13a` (rpm-requests/regulators-1/l13) is **already `regulator-always-on`, 1.78–1.95 V**. So
  on V74 the sensor was already powered, and the new vote changes nothing electrically; it only makes the dependency
  explicit.
- So "gpio75 always high" on V74 was **not a supply problem**. Likely causes: magnet too weak or held in the wrong
  place, or no pull-up (the V74 pin config of gpio75 is unknown; the overlay sets bias-pull-up).
- Kernel config: `CONFIG_KEYBOARD_GPIO=y`, `CONFIG_REGULATOR_FIXED_VOLTAGE=y`, `CONFIG_OF_OVERLAY=y` (no gpio_keys.ko
  needed).
- `a6l_hall_ovl.ko` builds.

`run-rest2.sh MODE=hall` is read-only. The L13 vote is a no-op on an always-on rail. The test loads the overlay (and gpio_keys.ko if it is a
module), prints the L13/hall regulator summary, then takes 20 samples of the gpio75 level and the hall IRQ count.
**Pass:** the level toggles and the IRQ count rises with a magnet.

**A weak fridge magnet may not trip the sensor.** Use the flip cover or a speaker/neodymium magnet held over the top
half of the phone, both sides. If gpio75 still never toggles with L13 confirmed on, the next step is the stock sensor
position from the stock DT/board photos.

Android: SW_LID is reported by InputReader (lid switch). Using it needs `config_lidControlsSleep`/`config_lidControlsScreenLock`
in an RRO (flash agent, optional).
