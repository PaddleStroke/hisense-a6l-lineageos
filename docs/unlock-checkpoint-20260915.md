## Exact firmware audit

The evidence is the captured ABL LinuxLoader and XBL VerifiedBootDxe, not an
assumption that an upstream Qualcomm implementation matches this phone.
`tools/Inspect-UnlockPersistence.py` checks these hashes and emits the private
report `firmware/extracted/stock-xbl-20260915/unlock-persistence-report.json`.

| Module | SHA-256 |
| --- | --- |
| LinuxLoader.efi | `6bbe53f345729c77c9a0ba74aa7f7aadb6cd68b0ac1511f6f160bc69de6ab523` |
| VerifiedBootDxe.efi | `53b0b13fdd3bd3ae563030f783277319f74bbf232b62e01262515fe21bd1e1fd` |

Both standard `flashing unlock` and `flashing lock` reach a common handler at
RVA 0x33e00. Its call at 0x33e4c invokes 0x146a8, which returns constant 1;
the handler therefore rejects with `Unlock is not allowed!` before the OEM
permission check. The physical permission result 1 does not bypass that gate.
The standard lock/unlock commands have not been attempted on the phone.

The `Hisense unlock` handler calls 0x23ee8, which sets both ordinary and critical
unlock bytes at offsets +0x0d/+0x0e in the runtime DevInfo structure. This function
does not write storage. `erase avb_custom_key` is a special command path, not an
ordinary GPT partition erase: it calls 0x245d0, clears custom key length +0x94
and its 0x800-byte buffer at +0x98, then persists the entire 0x998-byte DevInfo
structure through the device-info protocol. This saves the changed unlock flags.

XBL's VerifiedBootDxe installs that protocol with ReadWriteDeviceState at RVA
0x155c. Secure-monitor state selects protected-storage access through secure-app
commands 0x202/0x203, or a plain `devinfo` partition path. The branch taken on
this spare has not been directly observed; `secure:yes` does not distinguish
them. Captured GPT devinfo has both flags zero and custom key length zero, but
these bytes do not establish the live protected-storage contents.

The key-erasure special case returns OKAY without itself calling the standard
unlock wipe routine or scheduling reboot. The
[community A6L procedure at revision 067c4cd](https://github.com/tombaczynski/Hisense-A6L/blob/067c4cd763539d956da4f3554eed03491ada7d86/rooting.md)
reports a subsequent wipe prompt. That report uses firmware 6.08.03; this spare
has 6.01.04. Its exact first-boot behavior remains untested. Treat userdata as
potentially erased rather than relying on its preservation.

## Prepared operation and limits

The following operation was explicitly approved and has now completed. Do not
repeat it: its original locked/green preflight intentionally rejects the new
unlocked/orange baseline. `tools/Run-A6LLaptopTest.ps1 -VendorUnlock` launched the
reviewed laptop wrapper and `Run-LaptopUnlockPhase.py --apply-reviewed-unlock`.
The operation was:

1. Recheck the exact spare, original Android properties, battery at least 40%,
   host-client hashes, stock recovery hash and the known working USB setup.
2. Reboot to the bootloader and repeat the preflight queries.
3. Send `Hisense unlock` once using the guarded source-built client. Require
   OKAY and read back both unlock flags as true before proceeding.
4. Send `erase avb_custom_key` once using the official Google client. This clears
   the custom key and persists the changed security state.
5. Only after an acknowledged result, reboot to the existing Android image.
   Handle any on-device reset/setup prompt with Pierre and reauthorize ADB if
   required. Verify original fingerprint, boot complete and flash.locked=0;
   record the reported verified-boot state.

The script journals the persistence attempt before sending it. If that command
times out, fails or has an ambiguous result, it sends no automatic retry or
reboot. Inspect the saved evidence and phone state before any further action.
An interrupted runtime-only stage normally reboots to discard the temporary flags.

This phase changes both ordinary and critical unlock permissions. It does not
write bootloader firmware or install the diagnostic. The backup excludes
userdata, RPMB, eMMC hardware boot areas, fuses and separate e-ink SPI flash.
Firmware partition reads are proven; restoration after modification is not.
Neither a complete reversal of the security change nor normal relocking can
be promised. Restoring the captured GPT devinfo alone is not a proven relock.

An exact stock recovery image is hash-verified on both desktop and laptop:
64 MiB, SHA-256 `9688e3dfb349186fb60efc057a618aeaf696b030ad52974932ea83a077b31621`.
The one-partition EDL restore description is prepared; the known working EDL
read setup is on Windows. Laptop EDL and any EDL write remain untested. Before
replacing recovery, complete its executable restoration/readback procedure and
the diagnostic entry/exit plan in [the recovery checkpoint](recovery-probe-20260914.md).
