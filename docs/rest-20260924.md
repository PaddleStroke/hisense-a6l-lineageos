## 2. Vibrator: why nothing was felt (V45/V46) and what changed

Stock DT (`qcom,haptic@c000`, PM660 SID1): LRA, **direct** play, square wave, 6667 µs (150 Hz), **vmax 3200 mV, ilim 800 mA**, brake 3/3/0/0, auto-resonance **QWD** mode, `correct-lra-drive-freq`, clock-trim compensation.

Problems in the upstream `qcom-spmi-haptics.c` (pinned sha e83ffefb…) when used on PM660:
1. **Amplitude.** `magnitude = strong >> 8` gives 0..255, but vmax uses it as a percent: `vmax = 3480*mag/100 + 116`. The V45/V46 pulse (strong 8192) gave about 1.2–1.3 V, which is **40 % of the stock 3.2 V**, for 100 ms. That is the most likely reason nothing was felt. The same formula saturates at 3596 mV for anything above about 0x6400. That is **above stock**, and Android's HAL would hit it.
2. **Auto-resonance.** The driver programs the PMI8998 layout: register 0x4F set to ZXD_EOP, and auto-res on/off through **TEST2 0xE3 bit 7**. PM660 keeps auto-res in 0x4B (the driver defines it but never uses it) and has a different 0x4F layout. So the LRA drive frequency and a test register were changed wrongly.
3. The brake pattern was read as u8 while the DT has u32 cells (fixed earlier). The `play_lock` mutex is never initialised.

`device/hisense/a6l/kernel/a6l-pm660-haptics/a6l_pm660_haptics.c` (patch: `a6l-pm660-haptics.patch`, 246 lines) changes:
- Magnitude 0..0xffff is scaled linearly to a ceiling. The ceiling is `qcom,vmax-mv` (default **3200 = stock**, hard maximum 3200) or the module parameter `max_mv` if lower.
- In `pm660_mode` (the default), the driver writes nothing to 0x4F or TEST2. The LRA runs open-loop at 150 Hz. The brake pattern is read as u32. `qcom,ilim-ma` is supported. `mutex_init` is added.
- FF_CONSTANT is advertised, because the QTI VibratorOL AIDL HAL requires FF_CONSTANT or FF_PERIODIC.
- A register dump is printed at probe (`A6L_HAP probe …`) and exposed in `/sys/kernel/debug/a6l_haptics/regs`.

`a6l_vib` (static NDK) sends one bounded FF_RUMBLE: strength 0..65535, 1..1000 ms.

## 4. Fingerprint: likely infeasible

- **Sensor:** Sunwave (`sunwave,fingerprint`), platform device. Reset gpio20, IRQ gpio72 (`sf-irq`, 32 IRQs in stock), power gpio64 (`sunwave_ldo`). Input device `sf-keys`.
- **HAL:** `fingerprint.default.so` NEEDs `libQSEEComAPI.so`. It calls `QSEECom_start_app`/`QSEECom_send_cmd` with `SF_CMD_TA_*` (ENROLL, AUTHENTICATE, GET_AUTHENTICATOR_ID…) and logs `solution.qsee_spi_id : SPI_%d`.
- The only SPI QUP in the stock DT (`spi@c1b8000`) carries the e-ink NOR, so **the sensor's SPI bus is owned by TrustZone**. Image capture and matching run inside a Sunwave QSEE trusted app. Linux only sees the IRQ and reset.

Why it is infeasible on mainline:
- Mainline `qcom_qseecom` only supports querying already-loaded apps. It has an allowlist for `uefisecapp` on SC8280XP/X1E and no app **loading**. The stock path loads the TA from the firmware partition via the downstream qseecom ION/listener ABI.
- The TA also needs QSEE listener services (qseecomd: file storage/RPMB) for templates.
- Its authentication tokens are HMAC-signed with a key shared with the **QSEE keymaster** TA. A LineageOS build on mainline uses software KeyMint/Gatekeeper, so even a working TA could not unlock Keystore-bound credentials.
- A port would mean writing a downstream-compatible qseecom app loader + listener daemon for SDM660 TZ, plus a keymaster bridge: weeks of work, with a real risk that TZ rejects the calls.

Recommendation: ship without fingerprint (PIN/pattern). Revisit only if someone upstreams QSEE app loading for SDM660.

## 5. CPU frequency scaling (CPRh + OSM)

Found:
- Stock SDM660 uses the same scheme as MSM8998. The kernel programs the **OSM** LUT (`qcom,clk-cpu-osm`, rows `<freq freq_data pll_override spare corner>`), and two **CPRh** controllers (`cprh-ctrl@179c8000` apc0/pwrcl, `@179c4000` apc1/perfcl) supply per-corner voltages.
- The stock freq_data encoding matches the mainline 8998 port bit for bit: src bits 27:26, pll_div 25:24, core count 18:16, L-val 7:0. For example, 633.6 MHz = 0x05040021 = src1, div1, lval 33.
- **The fuse tables that were missing** (`sdm660_kbss_{init_voltage,target_quot,ro_sel,quot_offset}_param`, `sdm660_kbss_fuse_ref_volt`, speed bin {38,29,31}, fusing rev {71,28,30}) were **extracted from `stock-symbolized.elf`** with `research/rest-20260924/dump_cprh_tables.py` → `cprh-sdm660-fuse-tables.txt`.
- The layout was verified against the MSM8998 tables and the mainline msm8998.dtsi cells, which match exactly.
- The SDM630 data in the same ELF matches SoMainline's sdm630 values. The perf RO factors match the stock DT except RO1, which is 4230 on 660 and 3230 on 630.

Built (tree `/home/a6l/kernel/a6l-7.2-cpr`, out `/home/a6l/kernel/out-a6l-cpr`):
- CPR sources: cpr3.c, cpr-common.[ch], cpr.c and `include/soc/qcom/cpr.h` taken from SoMainline `topic/cpr3hh` (FETCH_HEAD dba854852), with Kconfig/Makefile entries. `remove_new`→`remove`.
- `qcom-cpufreq-hw.c`: the 6.10 cpr3hh version, because the series did not apply to 7.2 (5/15 hunks failed). Ported to 7.x: `devm_pm_domain_attach_list(PD_FLAG_REQUIRED_OPP)` instead of the removed `devm_pm_opp_attach_genpd`, `exit` returns void, boost via `cpufreq_boost_set_sw`.
- `add_sdm660.py` adds `sdm660_cpr_desc`, using stock values for APM 872 mV, hysteresis 20 mV, loop 5 ms, step 4 mV and quot init 12/14.
  - Per-fuse-corner ref/max/min/range/open- and closed-loop adjustments are derived from the stock ceilings/floors/fmax-map.
  - RO factors come from the stock DT.
  - **`hw_closed_loop_en = false` (open-loop first).**
  - `sdm660_soc_data` = the 8998 OSM offsets without ACD (the stock DT has no ACD).
- Result: `A6L_CPR_OBJ_BUILD_PASS`, **`A6L_CPR_IMAGE_BUILD_PASS`** (Image.gz sha e6191dae…, only 2 harmless warnings).
- `a6l-cpufreq-v75.dtso` (generated by `gen_sdm660_cpr.py`) merges onto the V74 DTB. It contains:
  - 40 qfprom nvmem cells
  - an 8-level CPRh OPP table (fuse-level map from the stock fmax maps)
  - pwrcl/perfcl OPP tables with the stock override/spare/div values
  - cpufreq_hw@179c1000 and apc_cprh
  - the CPU links (cpu0-3 = cpu@100 perf cluster → domain/thread 1; cpu4-7 = pwr → 0)
- **First bring-up is capped at the frequencies common to all speed bins:** pwrcl ≤ 1536 MHz, perfcl ≤ 1747.2 MHz.

Unverified (placeholders or assumptions):
- `max_volt_scale`/`max_quot_scale` (SDM630 values) and `sensor_range` (0..6). These only matter for closed-loop.
- `vdd_settle`/`corner_settle` timings (SDM630).
- Whether TZ allows the OSM sequencer `qcom_scm_io_writel` on SDM660, as on 8998.
- CX AO vote as the CPR power domain.

`a6l_cpr_openloop.py` computes, from a **read-only** fuse dump, the open-loop voltage every corner would get (downstream formula + stock clamps). Tested on synthetic fuses: A6L_CPR_OPENLOOP_SANE.

## 6. Charging, battery, thermal, suspend

- Hardware: PM660 SMB2 charger (SID0 0x1000) + FG gen3 (0x4000) + RRADC. SMB1351 parallel charger on `i2c@c176000` 0x1d.
- Stock policy: 3800 mAh, FV 4.40 V, FCC ≤ 2.4 A, ICL 2.0 A, JEITA 0/10/44/55 °C with warm/cool reductions, and step charging.
- Mainline `qcom_smbx` matches `qcom,pm660-charger`. It enables charging with a hard-coded 1.95 A FCC, float voltage from monitored-battery, and **no software JEITA**. PMIC hardware hard hot/cold limits stay at their OTP defaults. No SMB1351 driver exists: leaving it untouched keeps it disabled, so charging is slower but never above stock.
- Built: `a6l-charger-v75.dtso` (battery + FG + charger; supersedes `a6l-battery-telemetry.dtso`). Merges onto V74.
- Attended C2 (Pierre, **current-affecting**): V75 DT, cable plugged. Run `MODE=power` every 30 s for 15 min and `MODE=thermal`. Expect `STATUS=Charging`, current_now positive at ≤ 1.95 A, battery temperature rising by less than 5 °C. Unplug and replug, and confirm a clean stop. Abort above 40 °C battery temperature.
- Before daily use, add JEITA in software. The simplest route is a thermal-zone trip on the battery temperature that sets `charge_control_limit`/disables charging via the health HAL, or a small patch to `qcom_smbx`.
- Thermal:
  - Mainline sdm630.dtsi already has tsens (`qcom,sdm630-tsens`, CONFIG_QCOM_TSENS=y), 9+ CPU/GPU zones, and pm660 temp-alarm.
  - Stock has 29 zones, including battery, epd, emmc, pa, quiet and xo board thermistors on ADC; the mainline pm660 ADC has only xo_therm.
  - The thermal HAL (hals agent) should read the real `/sys/class/thermal` zones instead of fake values.
  - CPU passive cooling needs the cpufreq driver above.
- Suspend: s2idle only (`SUSPEND_FREEZER`). Plan:
  - Android autosuspend on s2idle.
  - Wakeups: PON key, pm8xxx RTC alarm, modem SMP2P/GLINK, charger plug IRQ.
  - Measure drain after the drivers are stable.
  - RPM deep sleep (CX/XO shutdown) is unvalidated on mainline SDM660.
