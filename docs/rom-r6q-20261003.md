# r6q — measured camera fixes and e-ink diagnosis

This candidate follows the r6p EV/settled-image tests. It is installed and booted;
physical acceptance remains incomplete. See `firmware/extracted/rom-r6q-20261003/status.json` and
`tools/Show-RomBuildStatus.cmd` for current progress.

## Included changes

* Camera RAW row cache and identity bypass preserve the tested pixel output while
  targeting the measured 146–152 ms resize bottleneck. Camera sensors themselves
  supply around 30 FPS; achieved preview FPS must be measured after installation.
* Validate exposure/gain controls before typed reads to avoid the reproduced
  provider assertion. Invalid controls complete metadata without guessed writes.
* Serialize ownership of the shared statistics block until the matching IPA
  consumer finishes. Stop/error/reentrant completion cases are covered. An
  isolated proxy instance cannot restart after stop; it requires recreation with
  a fresh shared block. Each configure logs the selected proxy mode.
* Correct Hi846 timing metadata only for the measured two-lane 1632×1224 mode.
  The empirical effective pixel-array rate is 288 MHz. Physical register tables,
  PLL/link/stream programming, kernel image and DTBO remain unchanged. This does
  not itself correct darkness or sensor exposure behaviour.
* Notify WM through its existing one-way Binder property-change path after exact
  appearance target/theme publication. Fresh-window and fence checks remain.
* Optional one-shot EPD trace saves the exact received raster and actual
  post-dither raster, for comparison with the same physical update. Normal
  pixels, waveforms, rails, history and policy remain unchanged.

## Diagnostic access and validation

The deployed trace property is **`vendor.a6l.eink.trace_once`**. The original
candidate's `debug.vendor.…` spelling failed the vendor namespace check; the
separate adapter passed the native gate, conversion and socket fixtures.

The attempted shell setter allowance also conflicts with Android's core-domain
vendor-property restriction. The final trial drops that allowance rather than
relaxing the restriction. Shell arming depends on the existing **permissive**
development ROM, confirmed on the physical r6p phone. Enforcement is unchanged.
It is not an enforcing-compatible diagnostic interface. Native userdebug/eng,
token and one-slot gates remain; the future enforcing version needs a properly
owned system debug property or a vendor diagnostic broker.

The completed system image changes only the switcher APK/odex/vdex and three
generated build-property files. All other system files match r6p. Camera payload
retains the signing key, HAL, worker and YAML inputs; signature and client ABI
checks pass. Full vendor-image inventory and actual-image checks precede flash.

No preparation pass, clock/rail changes or routine development-image snapshots.
The updater uses hash-only inventory, changed-partition writes and readback.

## Still unresolved and physical test order

### Attended results, 3 October evening

Hash-only installation completed at 21:26 Paris. System/vendor readback passed;
boot/DTBO were unchanged and skipped. Protected/userdata checks passed. The
receipt directory is 1,098,299 bytes; no development-image snapshots were made.
Android completed boot, and actual captures use the trusted threaded IPA.

Both rear cameras remain approximately 5 FPS. Measured median RAW resampling
is 155.8 ms main / 150.0 ms wide, with whole ISP processing 209.9 / 195.9 ms:
the row-cache candidate has not demonstrated a physical rear-preview speed gain.
Pierre finds selfie distinctly faster, approximately 15–20 FPS, though still
slower than stock. This is a user estimate pending a matching timing export.

Wide brightness eventually becomes normal. The recorded 47-second ramp goes
from 8.3 ms at 1× gain to 33.3 ms at 16×. Valid statistics arrive every four
processed frames (about 0.8 s), and the retained controller increases exposure
product by only about 7–8% per update in these dark frames. This identifies a
slow adaptation mechanism. Corrected wide exposure metadata now matches the
measured sensor cadence; no physical sensor clock programming changed.

Camera opening/switching remains unstable: Pierre reports three failed opens
before selfie succeeded. Repeated provider abort stacks point to
`PipelineHandler::stop`, separate from the earlier typed-control assertion.
Stop-time request/metadata cancellation is under investigation. Do not treat
the camera lifecycle as accepted. E-ink notification latency and the exact
artifact trace are still awaiting their physical test.

1. LCD baseline, then camera preview throughput, stop/reopen and switching among
   all three cameras; verify proxy mode and absence of new ISP/CSI faults.
2. Fixed illuminated target: AE settling and saved JPEG comparison. Poor contrast,
   uncalibrated colour, noise and AF precision are not claimed fixed. A genuine
   covered-lens capture is useful; the first purported covered pair still shows
   the desk and must not be used for black-level calibration.
3. Wide timing/control check: approximately 33.34 ms raw cadence with corrected
   returned durations, unchanged mode/link programming.
4. E-ink switching stage timestamps and a matched exact-raster/optical artifact
   test. Retrieve private files from recovery with userdata mounted ro,noload;
   no adb-root or broader file permissions.
5. Separate LCD-only and rear-screen sleep/wake tests with live diagnostics.

The stock refresh audit identifies about 350 ms extra neutral scans and a burst
retention difference, but establishes no safe reduced scan count. A bounded
capture-overlap implementation is isolated and excluded from r6q. Neither a
15–60 FPS promise nor a stock-equivalent camera-quality claim is justified yet.
