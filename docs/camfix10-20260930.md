## 1. Evidence (t32, camera11 = camfix9b)
The logs are in `logs/t32-cam11/t32-cam11.tar`, unpacked in `logs/t32-cam11/x/`. The laptop copy is `v75/logs/t32-cam11.tar`.

- **All 15 variants FAIL**, including every stock-RDI variant: srup, sign, srupign, srupsof, stock, stk406 and rup406.
  - The per-frame reg-update chain works: `rup_irq = rup_req ≈ sof` (272/272, 359/359, 446/446).
  - The stock bus-error ignore works (`be_i 1`).
  - Yet sof/done stays at 264/0, 360/1, 444/1 and so on, and maxl/frame is 9–18.
- **VBIF:** WRITABLE in all variants (stick 3/3). `mask_ac` is 0 and `mask_d0` is 0xff, so the camfix6–8 "LOST" was a RAZ artefact (camfix9 hypothesis 1). The VBIF is closed as a cause.
- **Invariant:** exactly one bus error (0xC94 bit0) at SOF 2–6.
  - The written extent of slot 0 is 0x1a280–0x5b180 (26k–93k words). The data head is `ffffffff ffffffff ffffffff`.
  - Dones are 0–2 per run.
  - `A6L_WM4_P` shows lines being written in isolated frames (sof#6: 4, sof#9: 5, sof#19: 9, and 0 in between). sof#9 has `head 0` and `lines 5`, so those writes did not start at line 0. The WM **trickles**: it does not restart per frame.
- **No UB overflow is ever reported.** IRQ_MASK_1 = 0x20000390 has bit 9 (WM0 bus overflow) enabled, and s1 bit 9 never fires in t30–t32. So the WM is not blocked with data piling up in the UB. Either very little data reaches it, or the overflow is not reported.
- **Nothing on the sensor/CSI side has been measured while streaming:**
  - `A6L_CSID0 irq#…` are reset-time IRQs. The CSID IRQ mask is `0x800` (RST_DONE only), so ECC/CRC/unbounded-frame events are never seen.
  - The status raw values differ between runs: `0x3af108ff`, `0x3aff28ff`, `0x3abf28ff`, `0x3af708ff`, `0x3ab108ff`.
  - The mainline sdm660 CSIPHY enables **no IRQ mask** (`irqs 0` in every run). Yet `A6L_CSIPHY0_STOP status 01 01 20 20 00 04 04 80 80 40 00 d5` (once `05 01 a0 20 00 14 04 80 82 40 04 d5`) shows latched, uncleared common-status bits.
  - The CSID test generator was proposed in camfix7 §"reading" and has never been run.
- **Detail from lens A, explained:** the "first word 0x4" of slot 0 comes from our own camfix6 bit7 probe. `a6l_fix_probe` rewrites word 0 of every written line with the fill value at each SOF (`camss-vfe-gen1.c`). It is not a hardware symptom.

## 2. The two analyses (verbatim summaries)
**Lens A (scattered/mis-mapped sg buffer), refuted about 90 %:**
- The camss SMMU SIDs c00..c03 map to cb0 (S1 translate, CFIE/CFRE, CLIENTPD=0, USFCFG=1). gfsr and FSR are clean, and there is no context-fault line.
- The ping/pong IOVAs 0xfd000000/0xfc000000 have the top-down, size-aligned pattern of iommu-dma.
- Fixed mode already uses `dma_alloc_attrs`.
- The written data is one contiguous 36–85k-word run crossing 36–83 separately mapped 4 KB pages. It stops at random offsets (a stall, not addressing).
- Proposed tests:
  1. `iommu_iova_to_phys` at START/BUSERR, plus cb0 FSR/TLBSTATUS in every IRQ.
  2. `DMA_ATTR_FORCE_CONTIGUOUS`.
  3. `iommu_set_fault_handler`.
  4. A 0xdeadbeef marker and a snapshot at BUSERR.

**Lens B (WM register programming), refuted about 85 %:**
- ADDR_CFG 0x2 (frame-based), IMAGE_SIZE 0, BUFFER_CFG = ADDR_CFG and IRQ_SUBSAMPLE 0xffffffff all match stock `msm_vfe47_axi_cfg_wm_reg`.
- The IOVAs are 32-bit and 16 MB aligned, and max = base + 0xece000 rounded as stock does.
- Writes stop at a random 128-byte (burst) boundary between 0x480 and 0x55280, which rules out an address, stride or overrun stop.
- The 0xC94 RDI bit is ignored by stock.
- Proposed tests:
  1. A 640×480-class frame.
  2. IRQ_STATUS_1 UB-overflow bits and bus status at every SOF.
  3. WM0 0xA0–0xCB at SOF 1–8.
  4. A hash of the written region (bars or 0xffffffff?).

## 3. Hypotheses for camfix10, ranked
1. **The data is lost before the VFE** (sensor → CSIPHY → CSID RX; ~40 %). If the D-PHY loses HS sync inside a frame (settle/lane timing), CSID drops the long packets (ECC/CRC). The short FS/FE packets survive, so SOF keeps counting.
   - The WM then gets only a few lines, which is exactly the trickle pattern (a few lines in a few frames, no UB overflow, no restart at line 0, frame-done almost never).
   - Both sensors fail identically. That fits a shared CSIPHY 3ph-1.0 / sdm660 configuration better than a VFE fault.
   - The latched CSIPHY status bits and the CSID status differences are consistent, but they are undecoded.
2. **The WM/VFE → MNOC write path stalls without reporting** (~35 %). The UB-overflow bit is not reported, or the stall is in the bus bridge.
3. **Frame size / line rate related** (~10 %). The test is the small TG frame.
4. **Memory mapping (lens A)** (~5 %). The test is contiguous slots plus the per-page iova→phys check.
5. Other (~10 %).

**The CSID test generator separates 1 from 2–4 in one capture:**
- Its frames never touch the sensor, the CSIPHY or the CSID RX.
- They follow the same CSID → ISPIF → VFE RDI0 → WM0 → SMMU → DDR path as the sensor frames.

## 6. Risks
- TG mode: the CSID CORE_CTRL registers are not written. The CSID is reset at power-on for every capture, so the stale sensor PHY selection is cleared. The sensor still streams into an ignored input.
- Bit 8 enables more VFE error IRQs. Each extra bit is masked again after 64 hits, and the original mask is restored at stop.
- Bit 4 uses up to 2 × 7.9 MB of the 32 MB CMA. Failure falls back to the normal allocation.
- The CSID/CSIPHY poll writes only their IRQ clear registers, the same ones their own ISRs write.
- The poll pointers are cleared at CSID/CSIPHY stream-off, and the VFE run flag is dropped before them.
