# Recovery USB "not attached": analysis, V75-usb candidate and no-flash workaround (agent `usbfix`, 24/25 Sep 2026)

**Status: V75-usb built and checked offline (captured-ABL emulation + mock-sysfs watchdog test). NOT flashed, NOT booted.**
`usb-kick.sh` is staged on the laptop and was run once in read-only `status` mode (phone was in stock Android at that time).
Nothing touched the phone.

## 1. What the evidence says

### 1.1 The laptop kernel log (read-only, `journalctl -k` over `lap.sh`)
Every stock → `adb reboot bootloader` → fastboot (18d1:d00d) → recovery cycle since 23 Sep noon, for port 3-2:

| stock enumerated (mono s) | fastboot at | stock time before reboot | time in fastboot | recovery (1d6b:0104) |
|---|---|---|---|---|
| 793437 | 793601 | 164 s | 21 s | **OK** 19 s after fastboot left |
| 793814 | 794019 | 205 s | 22 s | **OK** |
| 794185 | 794305 | 120 s | 126 s | **OK** |
| 795323 | 795380 | **57 s** | 51 s | **OK** |
| 798598 | 808990 | **10392 s** | 24 s | **FAIL** (nothing until stock came back 620 s later) |
| 809643 | 809738 | 95 s | 38 s | **FAIL** |
| 809975 | 811093 | 1118 s | 5 s | **OK** |

Conclusions:
- **Stock uptime does not predict the outcome** (57 s worked, 3 h failed). The "wait longer in stock" rule was luck.
  The time spent in fastboot does not separate the cases either.
- In the failures the laptop logs **nothing at all** for port 3-2: no "new high-speed USB device", no
  "device descriptor read" error, no over-current (`over_current_count=0`). The host never saw a D+ pull-up.
  So the fault is on the phone: the gadget is bound but the controller/PHY never presents itself on the bus
  (UDC `state` stays "not attached", which is what `A6L_USB_STATUS state=` then prints).
- The laptop port is healthy afterwards (stock and fastboot always enumerate on the same port).

### 1.2 Phone side (recovery sources and V74 DT/kernel)
- `a6l_android_probe` (`device/hisense/a6l/diagnostic/android_service.c`) configures the gadget at t=0, binds the UDC
  **once** at t=4 s, writes `soft_connect=connect` **once** at t=8 s and never retries. The kernel patch
  `a6l_manual_usb=1` (udc/core.c) holds the pull-up until that write. So any glitch at that moment is permanent.
- DT (V74 base.dtb): `usb@a800000` `dr_mode="peripheral"`, `maximum-speed="high-speed"`, no extcon/role switch;
  the legacy glue `dwc3-qcom-legacy` forces the QSCRATCH VBUS-valid override for non-host mode at probe
  (`UTMI_OTG_VBUS_VALID|SW_SESSVLD_SEL`, `LANE0_PWR_PRESENT`). dr_mode/VBUS signalling is therefore already
  "forced peripheral"; nothing to add there.
- PM660 charger node `charger@1000` is `disabled`; nothing in mainline drives PM660 APSD/HVDCP/Type-C.
  Those PMIC blocks are **not reset by a warm reboot** (sysrq, crash, `adb reboot`), only by a PMIC hard reset
  (long-press Power), which matches "long-press restart fixes it". Stock's `smb2_shutdown()` (msm-4.4) writes
  UFP mode / force-5V / APSD-enable on a *clean* reboot only, not on sysrq/crash. This is the best remaining
  hypothesis for a PMIC-side state that holds D+/D- (BC1.2/HVDCP detection driving D+) — **unproven**.
- QUSB2 PHY: mainline uses `msm8996_init_tbl` for sdm660 (TUNE1 f8, TUNE2 b3→efuse, TUNE3 83, **TUNE4 c0**,
  PLL_TUNE 30 …) with the CML (differential) reference-clock scheme; stock uses the same values except **TUNE4 0x0f**,
  and stock also votes `ref_clk_src` = RPM LN_BB_CLK1 (mainline only enables the GCC `clkref` gate; LN_BB_CLK1 stays
  on through `clk_ignore_unused` + RPM handoff). A TUNE4 difference would give enumeration errors, not total
  silence, so it is not the primary suspect. A missing LN_BB_CLK1 would make the PHY PLL fail to lock
  (`QUSB2PHY pll lock failed` → no UDC at all), which also does not match "state=not attached".
- Runtime PM: in good cases `runtime_status=active`; the watchdog pins the dwc3, glue and PHY devices to `on` anyway.

## 2. The fix: V75-usb = V74 + a USB re-attach watchdog in the ramdisk

| | sha256 |
|---|---|
| **V75-usb** `firmware/extracted/recovery-v75usb-candidate-20260925/recovery-diagnostic-unsigned.img` | `8ecb8e9e4c5289cfe63c23eb32b749178935a6588673cea3a1b1ebee3c94b304` |
| ramdisk.cpio.gz (new) | `404793070039f2404659f74afac863dcba0e32092d8b0fc39246db3770c892e8` |
| Image.gz-dtb / base.dtb (**identical to V74**) | `7e717e65…ebc191b` / `aceadcb7…98637e` |
| predecessor V74 | `24ede49b…19da62` |

Changes (only the ramdisk; kernel, DT, cmdline, DTBO, header layout = V74; DT markers stay `v74`/`v71`, so every
bundle `run.sh` keeps working):
- new `/system/bin/a6l_usb_watchdog.sh` (source `device/hisense/a6l/diagnostic/a6l_usb_watchdog.sh`, mksh + toybox only);
- `/system/etc/init/hw/init.rc` = `device/hisense/a6l/diagnostic/android-init-v75usb.rc` (old rc + `start a6lusbwd`
  after `start a6lprobe` + a `service a6lusbwd` block, root, `u:r:recovery:s0`, oneshot).

Watchdog logic (all lines on kmsg as `A6L_USBWD …`, i.e. on the LCD console and in `dmesg`):
1. waits 25 s (the probe's own bind/connect happen at 4/8 s), pins runtime PM `on` for dwc3/glue/PHY;
2. polls `/sys/class/udc/<udc>/state` every 2 s. `configured`/`suspended` = good (logs `A6L_USBWD CONFIGURED t=… after_level=N`).
   Bad for 12 s (30 s if stuck in `default/addressed/powered`) → escalate one level:
   - L1, L2: `soft_connect` disconnect → 2 s → connect (udc_stop/udc_start; in 7.2 `dwc3_gadget_soft_connect` does a
     core soft reset + run/stop);
   - L3: gadget `UDC=""` then rebind (retries while adbd rewrites its FunctionFS descriptors) + `connect`
     (needed because `a6l_manual_usb` re-arms the hold on every bind);
   - L4: `dwc3` core driver unbind/bind of `a800000.usb` (phy_exit/phy_init → QUSB2 BCR reset + PLL relock), rebind + connect;
   - L5: glue `dwc3-qcom-legacy` unbind/bind of `a8f8800.usb` (USB30 BCR reset, clocks, VBUS override re-applied), rebind + connect;
   - then 60 s pause and again from L1, forever. Worst case ≈ 25 + 5×12 s ≈ 1.5 min to the full-reset level.
3. before the first escalation it logs one read-only snapshot: UDC/gadget/ffs/adbd state, runtime PM, PHY driver,
   `clk_summary` lines for `ln_bb|clkref|usb|cxo` and `regulator_summary` USB lines — so the next bad boot finally tells
   us the cause (Pierre can photograph the LCD).
If no UDC exists at all, it tries `bind` of `a800000.usb` on the dwc3 driver and keeps going.

## 4. No-flash workaround for the installed V74 (nothing can run on the phone without adb)
Phone side (Pierre):
1. Unplug the USB-C cable **at the phone**, wait 5 s, plug back; laptop: `tools/usb-kick.sh wait 30`. (Costs nothing;
   restarts PMIC APSD if that is what holds D+/D-. On V74 the gadget stays bound, so a real re-attach needs only the pull-up.)
2. If still nothing: **long-press Power** (~10–15 s, PMIC hard reset — the only reset that clears PM660 charger/Type-C state),
   then Volume-down into fastboot → Recovery. Empirically the most reliable path today.
3. Prefer a clean `adb reboot bootloader` from stock over sysrq/crash resets before entering recovery.
4. Port: keep the established port **3-2** (AMD xHCI root port, behind PCI 0000:04:00.4). Another port does not change
   the phone-side failure, but a USB-2 hub with per-port power switching (uhubctl-compatible) would let the laptop cut
   VBUS, i.e. a remote "replug".
Laptop side: `~/A6L-usb-20260915/tools/usb-kick.sh` (repo `tools/usb-kick.sh`, sha `65f9ab05…afdb`):
- `status` (default, read-only): what is on PORT (default 3-2) and its mode (stock/fastboot/RECOVERY/EDL), port sysfs state,
  last kernel lines, uhubctl view.  `wait [s]`: waits for 1d6b:0104.
- `reset`: `usbreset` of the enumerated device (useless in the "nothing" case, useful for a wedged adb).
- `port-cycle`: `usb3-port2/disable` 1 → 0 (sudo password). Harmless; re-runs host connect detection, does not cut VBUS.
- `uhubctl`: VBUS power-cycle when uhubctl is installed and the hub supports it (not installed now; root ports likely no PPC).
- `kick`: wait → port-cycle → uhubctl → tells Pierre to replug. `xhci-rebind --force`: rebinds the whole controller
  (also drops the MediaTek Bluetooth on 3-3), asks for `YES`. Never reboots the laptop, never runs adb.
Checked: `bash -n`, `status` run read-only on the laptop (phone in stock: `109b:911f … stock Android`), usage path rc 2.

## 5. If V75-usb shows "never recovers" (PMIC hypothesis) — prepared ideas, not built
- Load the mainline PM660 charger driver (`CHARGER_QCOM_SMB2=m`, `qcom_smbx.c`, node `charger@1000` disabled today)
  as an attended experiment: it re-initialises USBIN/APSD. This changes charging → rail/power change → needs Pierre's go.
- Direct SPMI writes (APSD rerun `CMD_APSD`, HVDCP off in `USBIN_OPTIONS_1_CFG`) need a PMIC regmap write path that
  does not exist in the recovery today; not attempted.
- QUSB2 TUNE4 0x0f (stock) instead of 0xc0: kernel patch candidate only if bad boots show enumeration *errors*.
