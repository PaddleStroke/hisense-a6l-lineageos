# V46 controls follow-up

V46 preserves the physically validated V45 executable kernel, Android RAM
userspace, storage policy, authenticated ADB, LCD and front-touch configuration.
It adds one explicit PM660 GPIO11 input state matching the enabled stock DT:
normal function, VIN 0, 30 uA pull-up, and the stock low output-strength setting
(the pin remains an input). GPIO number, event code 616 and debounce are unchanged.

The independent Terra review is in
`research/controls-followup-20260918/gpio-independent-review.md`. The stock
control emitted thirteen complete press/release pairs, whereas V45 allocated the
correct IRQ but observed no interrupts during attended presses. Explicit pinctrl
is a hypothesis to test, not a proven explanation. Stock raw pull value zero
means a pull-up; it must not be translated to `bias-disable`.

Image SHA256: `ce3727dda592065becb883ef3fe663cb3579290edb841854e01f4fc49d02a3c6`.
Packaging, header/body roundtrip and captured ABL checks passed. There are eleven
scoped DT property changes, including references and the V46 diagnostic marker.
The recovery-selection overlay and command line remain unchanged.

The vibration module is a separate RAM payload. The Luna review confirmed the
four-u32 versus four-byte brake-pattern discrepancy and identified a malformed
length acceptance gap. The final revision 4 accepts only absent, exactly four bytes,
or exactly four u32 cells; no drive amplitude, pulse duration, current limit or
resonance algorithm change. The unchanged helper requests one low-strength
100 ms pulse. Software success requires independent physical confirmation.

The primary review rejected intermediate R2/R3 agent drafts: an invalid-value
error could fall through the original optional-property handling, and one
preparer selected an unconfigured build directory. Neither was installed.
R4 distinguishes absent from a present empty property and rejects invalid
lengths/values. Twenty tests execute the actual extracted C parser, including
downstream error handling, and five diskless QEMU ABI/load/unload checks pass.
Validated kernel source, configuration, Image and Module.symvers remain unchanged.
Final module SHA256:
`9e0c92f8af21e5ed269945de04887e46ebaadf554a5cac59e7f7902630acf3f8`.
The unchanged helper SHA is recorded in the controls-v46 payload manifest.

## Physical test sequence

1. Verify staged image, tools, payload and known stock restore; install V46 only
   over the exact verified V45/stock recovery, preserving other regions and BCB.
2. Copy and independently verify all twelve before/after readbacks. Return to
   stock Android with Power, then select Recovery from the confirmed fastboot menu.
3. Use the short authenticated ADB readiness gate. No repeated storage benchmark
   or filming. Create only known input device nodes on diagnostic tmpfs.
4. Capture key events and interrupt counts during coordinated e-ink-button
   presses. Report successful capture separately from actual code-616 events.
5. Load the verified corrected haptic module, create its input node, and run one
   attended bounded pulse. Ask whether vibration was felt.
6. Save evidence and return to stock Android; verify laptop service restoration.

If the key still produces no events, preserve interrupt and boot evidence and
review PMIC pin/IRQ state rather than changing key codes. If vibration remains
imperceptible, review stock resonance/startup before changing output strength.
These outcomes do not block independent Android input/framework work.

## Primary-source cross-check

The 18 September online search found the downstream
[PM660 configuration](https://android.googlesource.com/kernel/msm/+/android-msm-wahoo-4.4-oreo-m2/arch/arm/boot/dts/qcom/msm-pm660.dtsi)
using a four-byte brake pattern and QWD resonance. The accompanying
[Qualcomm binding](https://android.googlesource.com/kernel/msm/+/a31dc311c827d6b522e0f219c6213d4399bcaa06/Documentation/devicetree/bindings/leds/leds-qpnp-haptics.txt)
distinguishes PM660 resonance options from earlier PMICs. This supports reviewing
PM660 resonance/startup if the bounded corrected-pattern pulse remains unfelt;
it does not prove a root cause or justify increasing drive strength. The search
did not establish a published A6L-specific GPIO11 fix.

Installation completed on 18 September at 08:27 UTC. All twelve copied readbacks
passed independent desktop verification; other checked regions and BCB were
preserved. Poweroff was acknowledged, EDL disconnected and host services were
restored. The current operation is recorded in `resume-next-session.md`.

## Physical results, 18 September 08:35–08:37 UTC

Authenticated ADB readiness and baseline passed. The PM660 debug view showed
GPIO11 as input, normal function, VIN 0, 30 uA pull-up and low strength.
The coordinated key recording captured **52 presses and 52 releases**, code 616.
Its IRQ count advanced from 103 to 211 (the user was already pressing before the
capture). Thus the explicit stock-equivalent pin state is sufficient to restore
the key in this diagnostic; this test does not isolate which field was required.

The R4 module loaded and the unchanged 100 ms low-strength pulse command passed;
the user explicitly reported **no vibration felt**. Correct brake parsing alone
does not resolve physical vibration. Do not mark the component working or
increase output strength without reviewing PM660-specific startup/resonance.

Evidence is archived in `captures/capture-controls-user-v46/`, with `analysis.json`
and a SHA256 index. No film was needed. The user has been asked to return to stock
Android. Stock identity/boot completion and host-service restoration were verified
at 08:38:57 UTC; the final session report is archived and no capture remains active.
