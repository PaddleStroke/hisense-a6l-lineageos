# camfix6: RDI write master starved on the AXI side, not by the VFE clock (28 Sep 2026)

Status: **built and checked offline only. Not run on the phone.** qcom-camss.ko compiles against the 7.2.3 tree with only the
two old `-Wmissing-prototypes` warnings. Bundle staged to the laptop: `sha256sum -c` 23 OK / 0 bad.

## 1. Evidence (t28b, camera6 = camfix5, `MODE=clkloop FDUMP=24`)
Logs: laptop `~/A6L-usb-20260915/v75/logs/t28b/{c6-clk.log,dmesg-cam6.txt}`, repo copy `.relay/outbox/cam28/`.

| run tag | actual VFE clk | sof | done | buserr | reg-update ack at | bus error seen at |
|---|---|---|---|---|---|---|
| vfe120 | 200 MHz | 225 | 0 | 1 | SOF#1 | SOF#2 |
| vfe300 | 404 MHz | 393 | 1 (4.3 s late) | 1 | SOF#3 | SOF#4 |
| vfe404 | 480 MHz | 239 | 0 | 1 | SOF#5 | SOF#6 |
| vfe480 | 540 MHz | 225 | 0 | 1 | SOF#4 | SOF#5 |

- **The clock does not matter** (camfix5 ruled out).
- The bus error (s1 bit4, 0xC94 = WM0) always lands in the **first frame after the RDI0 reg-update ack**, which is the
  first frame the WM writes. s1 bit4 is not in the IRQ mask, so it is seen on the next SOF.
- 0xC94 then stays 1 (sticky, and s1 bit4 never rises again). 0x338 never toggles, and done stays at 0.
- There is no SMMU fault, no global fault and no CSID/ISPIF error, and the sensor streams.
- The WM block equals stock: ping/pong + MAX, ADDR_CFG 2, BUFFER_CFG 2, UB 0/682, CGC, 0xCEC enable, XBAR 0xc00, RDI_CFG 7.
- With the t27 wm4 scans (5..93 of 2156 lines ever written, max = 0 or +15 MB alike), this is an **AXI/memory-side
  starvation or stall of the RDI WM**. It is not a VFE-core throughput limit, and not a max-address or frame-size mismatch
  (a size mismatch would still write almost the whole frame).

## 3. Changes: `device/hisense/a6l/kernel/camera/patches/camfix6_patch.py` (after camfix..camfix5)
- Cumulative diff: `patches/camss-sdm660-camfix6-cumulative.patch` (1245 lines).

New runtime param **`qcom_camss.a6l_v6`**, default **0x0f**:
| bit | effect |
|---|---|
| 1 | stock VBIF settings (ioremap 0x0ca40000) at first stream-on, in `vfe_set_qos` |
| 2 | WM0 UB = 1904 words at offset 0 (VFE1 1392). Applies only when WM0 is RDI and the only stream |
| 4 | ICC vote `a6l_icc_avg`/`a6l_icc_peak` kBps (default 2000000/4000000) at stream-on (process context) |
| 8 | recovery: at RDI SOF, a NEW 0xC94 bit is written back (W1C attempt) and that WM is reloaded (once per new bit) |
| 16 | RDI WM line-based, stock formula (IMAGE_SIZE + BUFFER_CFG burst 3 + stride) |
| 32 | frame-based BUFFER_CFG burst field 3 |
| 64 | stock RDI UB 192 words (0xBF), a control |
| 128 | (`a6l_wm=4` only) progress probe, see below |

Read-only diagnostics:
- `A6L_AXI` gives the MMSS AXI RCG 0xc8cd000 cmd/cfg, which tells us the source and divider, i.e. the NoC AXI clock actually in use.
- `A6L_VBIF PRE/START/STOP` gives the VBIF QoS registers plus XIN_PND_ERR/SRC_ERR (0x190/0x194). It is read only while the VFE is powered.
- `A6L_ICC …` confirms the vote was applied.
- `A6L_VFE0_RECOVER#k` logs each recovery.
- `A6L_VFE0_V6 STOP v6 … rec … ub0 imgsize0 bufcfg0` summarises the run at stream-off.
- **Probe** (bit 128), one `A6L_WM4_P sof#k … slot0 head H lines N slot1 …` line per SOF (up to `a6l_pdump`=40):
  - `lines N` is the number of lines the WM wrote into the slot **during the last frame**.
  - How it works: word 0 of each written line is re-filled after every probe.
  - `head 1` means the WM restarted the slot.
  - This is the direct answer to "a few lines, then stall" versus "a few lines every frame".
- Every access is guarded: VBIF only while `power_count > 0`, ICC only in process context, and the probe only in fixed mode.
  Stream-off is unchanged.
- The camfix5 knobs (`a6l_vfe_min` 404 MHz default, `a6l_fdump`, `a6l_ub`, `a6l_wm`) are kept.
  `a6l_ub` still overrides the UB when it is set.

`run-camera.sh`:

**Reading the sweep table**
| pattern | reading / next |
|---|---|
| one variant PASS with done≈sof, max_lines ≈ 2156 | that bit is the fix: make it (only) the default; for the ROM, add camfix4+5+6 to the r4 kernel series |
| probe lines grow with UB (ub192 < base < ub1904) but none reaches 2156 | UB overflow from AXI latency: look at the AXI kHz (NoC clock) + VBIF; next is a higher ICC vote or the mnoc QoS (prio) |
| `base` probe: N lines in frame 1, then 0 forever (head 0) | the WM stalls after the first error: `recov` should restore per-frame writes; if not, the AXI writes never complete (VBIF pnderr/srcerr non-zero? SMMU) |
| `line` PASS but frame-based variants fail | the vfe48 RDI must be line-based like stock: default a6l_v6 bit4 |
| all fail, VBIF pnderr/srcerr ≠ 0 | VBIF error: send the dmesg (VBIF lines give the xin) |
| all fail, `A6L_AXI … ~19200 kHz` or ROOT_OFF | the MMSS NoC AXI clock is not scaled (RPM mmaxi vote not effective): the next fix is in the interconnect/rpmcc, not camss |

## 5. Risks / unknowns
- **Not verified on HW.** Which difference is the cause is still open. The default 0x0f combines the four stock-parity
  settings (VBIF, UB, vote, recovery), and the sweep isolates each one.
- 0xC94 write-back semantics are unknown: it may be W1C or it may be ignored. The recovery reloads each WM only once per new
  error bit, so a sticky 0xC94 cannot cause a reload storm.
- A reload in the middle of a stream re-latches ping/pong. In wm3 this could hand one torn frame to userspace after an error.
- The VBIF writes are the stock values. The VBIF is shared with VFE1 and CPP, which upstream does not use.
- The AXI RCG is RPM-owned but Linux-readable (mmcc registers it with clk_rcg2_ops), so it is read only, never written.
