## 1. Evidence (t30, camera9 = camfix7)
The t30 logs are in `logs/t30-cam9/t30-cam9.tar`, unpacked in `logs/t30-cam9/x/`. The laptop copy is `v75/logs/t30-cam9.tar`.

- **All 10 sweep variants fail** (base, hts2, hts4, clk, iccmax, clkicc, smmu, smmuall, smmuhts2, all). The best result is done = 1.
  - Each variant shows one bus error at SOF 1–5, after which the WM trickles 0–5 lines per SOF.
  - The front camera s5k3t1 fails the same way (sof 822, done 0, buserr 415). The cause is therefore in the shared VFE/VBIF/NoC path.
  - hi846 gives only 2 SOF and no stream. This is a separate issue (sensor/PHY side) and is not addressed here.
- **MMPLL4 is off in all 142 register dumps** (START, BUSERR and STOP, in every run):
  - `mmpll4:mode 00000000 L 40 (768 MHz) nolock`.
  - MODE = 0 means OUTCTRL, BYPASSNL and RESET_N are all clear, with no FSM vote and no LOCK_DET. The PLL is disabled, not merely unlocked.
  - The same dumps show MMPLL0 as `c0118000` (FSM-voted and locked), MMPLL7 as `c0000007` (manually on and locked), and MMPLL10 turning on during the stream.
- **The MMSS NoC AXI RCG runs from MMPLL4.**
  - `axi_clk_src` (MMCC 0xd000, "RO to linux", owned by the RPM) reads `cfg 00000203`.
  - In the mainline map `mmcc_xo_mmpll0_mmpll4_mmpll7_mmpll10_gpll0_gpll0_div_map`, source 2 is **P_MMPLL4**. HID 3 means ÷2, so the nominal rate is 384 MHz.
  - This source is not in the RPM/stock table, which contains 75, 171.4 and 240 MHz from GPLL0, and 323.2 and 406 MHz from MMPLL0.
  - clk_summary agrees: `mmpll4` has enable 0, prepare 0 and hw-enabled **N**, and `axi_clk_src` is its child with enable 0.
  - The AXI branches (`camss_vfe_vbif_axi_clk`, `throttle_camss_axi_clk`, `bimc_smmu_axi_clk`, `mdss_axi_clk`) have **no parent in Linux**, so the clk core never keeps MMPLL4 enabled for them.
- **Correction to camfix7 §1.4.** "AXI ~0 kHz was a decode bug" was only half right.
  - The source index was decoded wrongly before camfix7.
  - But camfix7's 384 MHz figure comes from the L value alone, and the PLL behind it is **disabled**.
  - The branch CBCR "on" bits and the RCG ROOT_OFF = 0 are sampled status flip-flops. They go stale when the source stops, so they do not prove a running clock.
- **The VBIF writes never stick** (camfix6 and camfix7): `wgather(ac)` stays 0 after 0x40 is written, and `outrd(d0)` stays 0x10 after 0x1010 is written.
  This is what an unclocked VBIF core (the AXI domain) would show, while its AHB register interface still answers.
- **SMMU `fsr 00000400` is not a fault.** In SMMUv2, FSR[10:9] is **FORMAT**, and 0b10 means an AArch64 context-bank format. It is read-only information.
  - The fault bits are 1–8, 30 (SS) and 31 (MULTI), and all of them are 0.
  - Together with GFSR 0 and FAR 0, the SMMU recorded **no fault**.
  - Clearing the FSR does nothing: the FORMAT bits are not W1C, and nothing is stalled because SS = 0.
  - Mainline `ARM_SMMU_CB_FSR_FAULT` also excludes FORMAT. The camfix7 "SMMU hypothesis" is therefore demoted.
- The cmdline carries `clk_ignore_unused` (V74 recovery cmdline, docs/flash-20260924.md), so `clk_disable_unused` should not be what turned MMPLL4 off.
  Camfix8 prints `CMDLINE clk_ignore_unused=` so the V75 boot can be checked directly.
  - The remaining candidates are the bootloader or RPM leaving the RCG on an MMPLL4 they then disabled, and mainline `clk_alpha_pll_configure(mmpll4)` rewriting CONFIG/USER_CTL of a running PLL at mmcc probe.

## 2. Hypotheses, ranked
1. **The MMSS NoC AXI clock has no running source** (confidence: medium-high; ~60–70 %).
   - The RCG sits on MMPLL4, and MMPLL4 is disabled. The VFE, VBIF and SMMU TBU on that NoC crawl or stall.
   - The first write that times out gives the 0xC94 bus error, and recovery cannot help.
   - This explains why every bandwidth, SMMU, UB and line-rate variant fails the same way, why the front camera fails too, why the VBIF writes are lost, and why there is no SMMU fault.
   - Open point: how any lines are written at all (a few per SOF). A glitching or partially running root is possible, and camfix8 measures this indirectly through the VBIF write-stick probe.
2. **The RPM MMAXI vote is not effective.**
   - `mas_mnoc_bimc` aggregates to INT_MAX, yet the RCG never leaves 0x203. Stock would have it at 406 MHz on MMPLL0.
   - If hypothesis 1 is confirmed, the ROM fix is to give the clock a live source from HLOS. If the RPM should do it, the icc-rpm mmaxi request needs to be traced.
3. **An NoC/xPU error response** (for example a buffer PA in a region protected for MMSS masters). This is next only if the AXI clock is proven alive and the VBIF writes stick.

Ruled out or demoted: SMMU fault (FSR FORMAT only), SMMU impl-defs and ACTLR, NoC/SMMU branch clocks, ICC 6/8 GB/s, line rate ÷2 and ÷4, UB depth, VFE core clock.

### PASS criteria
- Probe: `CAMSS_CAMFIX8_PASS`, `V8_DEFAULT 1`, and the 4 sensor `_PROBE_PASS`. Record `CMDLINE clk_ignore_unused=`.
- The diagnosis is **confirmed** when all three of these hold:
  - `base` shows `pll4_st 00000000` and `vbif LOST`.
  - `pll` shows `A6L_V8 CLK ON … parent mmpll4 hw_on 1`, mmpll4 mode `c0000007` (lock 1) and `vbif ok`.
  - `pll` has done ≫ 1.
- **Fix PASS** for a variant: done ≥ 0.9 × (sof − first), be = 0, maxl/frame ≈ 2156 and `CAPTURE_…_PASS`.
  Then run `raw10_to_png.py <raw> 2880 2156 3600 RGGB` on the host and check for colour bars over the full height.
- `posthold` or `post406` passing means the fix persists across streams without camera-side action. That is the model for the ROM fix.

## 5. Risks
- Enabling MMPLL4 uses mainline's own configure values (L 0x28 = 768 MHz, config 0x4001055b). It is the same operation the clk core would do for any consumer. Low risk.
- The 406 MHz variant rewrites an RPM-owned RCG. The RPM may later override it, or the write may be refused (WARN "rcg didn't update", which is not an oops). It also affects MDSS AXI, since it is shared; the rate step from 384 to 406 MHz is small. It runs last.
- Bits 4, 8 and 16 persist until reboot. Reboot before any unrelated camera comparison.
- If the AXI was dead since boot, the LCD/earlycon framebuffer in recovery must not have depended on it. Note whether the screen changes when the pll variants run.
- hi846 (2 SOF) is unrelated and stays open.
