# camfix5: why no frame after frame 0 (VFE clock too low, WM0 unified buffer overflows mid-frame) — 27 Sep 2026

Status: **built and checked offline only. Not run on the phone.** The module compiles against the 7.2.3 tree, with only
the two old `-Wmissing-prototypes` warnings. The bundle was staged to the laptop and checks 23 OK / 0 bad.

Readings:
- Across 5 different WM set-ups, the WM **never writes more than ~93 of the 2156 lines** of a frame, and the WM0 bus error
  arrives in the first frame. So camfix4's MAX address is not the limit: the max was 15.5 MB away, or 0, with the same result.
- The two "frame 0" captures are **false frames**: a done slipped through seconds later, and the copied slot was mostly
  0xA5 fill. "TIMEOUT waiting for frame 1" is the normal state, not a second failure.
- Everything upstream of the WM is healthy:
  - The sensor streams at ~30.7 fps (A6L_SNS_FC).
  - RDI0 SOF arrives on every frame (s1b29 = 217..396 per run).
  - The ISPIF and CSID show no errors, and there are no SMMU faults.
- **`A6L_VFE0 vfe0 rate 120000000 (min 60440427)`**: upstream sizes the RDI clock as `pixel_rate * bpp / 64` (64 bit per
  clock) and chooses the lowest level, 120 MHz.
- **Stock never clocks the VFE below 404 MHz.**
  - `firmware/extracted/device-trees/stock-00.dts`, `qcom,vfe0@ca10000`: the `qcom,clock-rates` levels for vfe_clk_src
    are 0x18148d00 / 0x1c9c3800 / 0x22551000 = 404 / 480 / 576 MHz.
  - msm_isp sets the VFE clock to at least the sensor op_pixel_clk, which means 1 pixel per clock, even for RDI.
- The stock ELF (`msm_vfe47_get_overflow_mask` = 0x09fffe7e) includes s1 bit4 in the **overflow** mask.
  `msm_vfe48_get_bus_err_mask` reads 0xC94 per WM. Stock treats this as a bus overflow, then halts the AXI and runs userspace recovery.
  So the camfix3/4 reading ("RDI bus errors are normal and ignored") was wrong.
  The ignore mask (`msm_vfe48_set_bus_err_ign_mask`) exists only for WMs that are writing to a scratch buffer.

## 2. Root cause (hypothesis, strong)
At 120 MHz the RDI write path drains the WM0 unified buffer (682 words) slightly slower than the sensor fills it:
- The input is 3600 B per line at about 14.4 µs per line, which is about 250 MB/s.
- A drain of about 2 B/clk at 120 MHz gives about 240 MB/s.
- So the UB gains about 120–150 B per line and overflows after roughly 70–90 lines. That matches the 55–93 lines seen.
  (The run with 20 lines had CGC off.)

The overflow is flagged as the WM0 bus error (0xC94 bit0 / s1 bit4). The frame is then broken, so no ping-pong done comes,
and the same thing happens on every frame.

Ruled out or secondary:
- WM re-arm, ping-pong address and RUP: the frame-based WM needs no per-frame address or RUP. The wm4 mode never changes addresses and still fails.
- Framedrop pattern/period and IRQ mask: done bit 8 is enabled (mask 0x80000120), and the done did fire when a frame completed.
- CSIPHY/CSID settle: SOF arrives on every frame and the CSID has no errors.
- Sensor streaming only one frame: its frame counter keeps moving.
- VBIF QoS (0xca40000: 0x124/0xac/0xd0) is still not applied. It is the next suspect if 404 MHz alone is not enough.

## 3. Changes (`device/hisense/a6l/kernel/camera/patches/camfix5_patch.py`, applied after camfix..camfix4)
Cumulative diff vs 7.2.3: `patches/camss-sdm660-camfix5-cumulative.patch` (1034 lines).
Build: `device/hisense/a6l/camera/tools/build-camfix5.sh` (WSL build dir `/home/a6l/camfix5`, `src-snapshot/`).
1. **Fix:** `a6l_vfe_min` default is **404000000**, the lowest stock level (MMPLL0/2 in mmcc-sdm660). It is also used in
   `vfe_check_clock_rates`. Setting `0` restores the upstream 120 MHz.
2. **Frame accounting:** at each stream-off the driver prints
   `A6L_VFE0_FRAMES STOP sof S done D buserr B first_buserr_sof F logged L`.
3. **Fallback diagnostic mode** `a6l_fdump=N` (default 0): for the first N events (RDI0 SOF, WM done or bus error), one line each:
   `A6L_VFE0_F <SOF|DONE|BUSERR> sof#k t <µs> s0 s1 pp(0x338) be(0xC94) cgc(0x3C) wm<n> cfg ping pmax pong qmax addrcfg ub imgsize bufcfg pattern subsample`.
   `a6l_fdump_wm` selects the WM (default 0).
4. **Experiment** `a6l_ub=<depth>`: sets WM0's UB depth at offset 0, where upstream uses 682. Use it only with a single RDI stream.
   This is a discriminator, not the fix.
5. `run-camera.sh`:
   - The dmesg mark is now a timestamp instead of a line count. The ring buffer wraps, and in t27 every `.dmesg` file came out empty.
   - New knobs: `FDUMP=`, `FDUMP_WM=`, `UB=`.
   - New summary lines: `RATE`, `FRAMES`.
   - Probe marker: `CAMSS_CAMFIX5_PASS` + `VFE_MIN_DEFAULT`.
   - **New `MODE=clkloop`**: one bars capture per clock in `VFES` (default `"120000000 300000000 404000000 480000000"`)
     with `WM=${WM:-3}`. The summary goes to `/tmp/cam-<sensor>-clkloop.sum`. At the end the loop restores `a6l_vfe_min=404000000` and `a6l_fdump=0`.

Files (new, nothing overwritten):
- Bundle **`firmware/extracted/camera-20260927-camfix5/`** = laptop **`~/A6L-usb-20260915/v75/camera6/`**. `SHA256SUMS` checks 23 OK / 0 bad on the laptop.
  - Only `qcom-camss.ko` (sha `f9ce7705…`) and `run-camera.sh` (sha `c480fa18…`) differ from camera-20260926.

## 5. Risks / unknowns
- **Not verified on HW.** The 2 B/clk figure is inferred from the numbers. What is certain:
  - the clock is 120 MHz, versus stock ≥ 404 MHz;
  - the overflow-type error happens in the first frame;
  - the WM stops after 20–93 lines in every set-up.
- Mainline mmcc-sdm660 does not vote a CX corner per VFE rate. Stock uses SVS_L1 for 404 MHz. With the display on, CX is
  normally at SVS or higher. The clock loop's 300 MHz point (GPLL0) is the fallback.
- `a6l_ub` overlaps the UB of WM1/WM2 if they run at the same time. It is for experiments only.
- The ROM (r3) still carries camfix3, so r4 needs camfix4 + camfix5 in its kernel series before the camera can work there.
