## 1. What was found

### Motion sensors and compass
* **The compass is on the ADSP, not on the AP.** The stock DT has no AK09918, AKM or magnetometer node. The stock
  `vendor/etc/sensors/sensor_def_qcomdev.conf` lists it as "SSI SMGR Cfg 2 AK09911_FIFO" on i2c_bus 3, which is the SSC bus
  of the ADSP. The live stock name identifies an AK09918 (docs/power-sensors-preparation-20260917.md). SMGR is therefore
  the right path. The mainline `ak8975` driver (it knows AK09918) is **not needed**, and it would fight the DSP for the bus.
  `CONFIG_AK8975` is not set in v67; no overlay or driver was prepared, deliberately.
* The kernel side is `drivers/iio/common/qcom_smgr` + `qcom_smgr_{accel,gyro,mag}` (Yassine Oudjana's series). Its IIO names are
  `qcom-smgr-accel`, `qcom-smgr-gyro` and `qcom-smgr-mag`. V71 proved on 21 Sep that all three devices appear.
* The facts that matter for any reader of these devices:
  * Channels are x, y and z as `le:s32/32`, plus a timestamp. There are **no `_raw` attributes**, so data only comes through the
    kfifo buffer (`buffer/enable` + `/dev/iio:deviceN`).
  * Scale = 1/65536 (SMGR Q16). The units are m/s² for the accelerometer and rad/s for the gyroscope. The magnetometer is
    expected in **gauss** (×100 → µT). The tool detects this automatically and prints `A6L_IMU_MAGUNIT`.
  * The sample rate is always the sensor's native maximum. Writing `sampling_frequency` changes only the reported value
    (qcom_smgr_request_buffering ignores it).
  * The frame is **NED**. The driver's mount matrix is `0 -1 0; -1 0 0; 0 0 1`. The test maps raw → Android with the classic
    QTI conversion `+y+x-z` (Android X = raw y, Y = raw x, Z = −raw z). The `flat` step checks this on the phone
    (`A6L_IMU_GRAVITY … map OK`). If the check fails, re-run with `MAP=…`.

### Android sensors HAL (important: the ROM's accel/gyro HAL does not work as merged)
* `rom.mk` ships `android.hardware.sensors@2.1-Google-IIO-Subhal` (trout) with `hals/sensors/sensor_hal_configuration.xml`
  (qcom-smgr-accel and -gyro). The trout source in our tree (`device/google/trout/hal/sensors/2.1`, unmodified) **cannot
  expose the SMGR devices**:
  1. `SensorsSubHal.cpp` isSensorSupported() hard-codes the only accepted IIO names, `scmi.iio.accel` and `scmi.iio.gyro`.
     The config XML does not extend this list, so the qcom-smgr-* devices are filtered out and **the HAL lists 0 motion sensors**.
  2. `Sensor.cpp` knows only ACCELEROMETER and GYROSCOPE. There is no MAGNETIC_FIELD at all.
  3. processScanData reads **every channel as int64** at `index*storage_bytes`, but SMGR channels are s32. It also expects
     `*_raw_available` (range) and a plain `sampling_frequency_available` list, while SMGR gives the IIO_AVAIL_RANGE form `[1 1 N]`.
* **Consequence:** rom.mk declares `android.hardware.sensor.accelerometer/gyroscope` features that the booted ROM would not
  provide (auto-rotate dead, and a CTS/feature mismatch). I did **not** add the magnetometer to the XML. Doing so would change
  nothing with trout, and the compass feature must stay withdrawn (ledger R2/R13) until a HAL serves it.
* **Recommended fix (for the HAL owner or the flash agent, not done here):** serve accel, gyro and mag from our own legacy module
  `sensors.a6l` (`hals/sensors/stk3338/sensors_a6l.c`, already loaded by Lineage's `sensors@2.0-subhal-impl-1.0` in the
  multihal), and drop trout from rom.mk and hals.conf. The IIO buffer logic is exactly what `a6l_imu.c` does (find by name,
  enable scan elements, parse `_type`, read records, ×scale, map `+y+x-z`, mag ×100). Add these handles:
  * `SENSOR_TYPE_ACCELEROMETER` and `GYROSCOPE` (continuous; minDelay from the native rate);
  * `MAGNETIC_FIELD_UNCALIBRATED` (raw µT + bias);
  * `MAGNETIC_FIELD` (raw − bias).

  **Calibration:** Android's framework does **not** compute hard-iron calibration. SensorService's fusion (rotation vector,
  orientation, compass apps) consumes the HAL's *calibrated* TYPE_MAGNETIC_FIELD. Stock did this in the SSC/ADSP
  (sensors.ssc, "mag cal"). The SMGR primary data we read is uncalibrated.

  So the HAL needs a simple running hard-iron estimator. A min/max or least-squares sphere fit over the last N samples that
  span enough directions is enough; the `turn` step of this bundle computes the same horizontal centre. The HAL should
  persist the bias in `/data/vendor/sensors/mag_bias`, report accuracy UNRELIABLE → HIGH as coverage grows, and fill
  `uncalibrated.bias`.

  Only after that is done and proven should `android.hardware.sensor.compass.xml` be shipped and removed from
  `a6l-unavailable-features.xml`.
* After the fix, the attended check is: booted ROM → `dumpsys sensorservice` lists the accelerometer, gyroscope, magnetic field
  (+ uncalibrated), STK light/proximity, and the virtual sensors (rotation vector, gravity, orientation).

### Loudspeaker (TFA9894)
* The ROM DT already uses `kvoice/dt/a6l-voice-speaker-onbase-v75` (ledger line 17). So the runtime overlay of this test is
  **exactly the ROM's DT #1 audio part**. A pass validates the ROM DT directly.
  * The fdtoverlay onto the V74 base gives `A6L_VOICE_DT_CHECK PASS voice_pcm_device=2` and
    `A6L_DT_CHECK PASS rule=reg --expect-tfa`, with chosen `kvoice-speaker-onbase-v75` and amp `nxp,tfa98xx`.
  * The link order is MM1, MM2, VoiceMMode1, Speaker Playback, Int PB, Int Cap. The pcm numbering is therefore the same
    as audio6: MM1 = 0, MM2 = 1, voice = 2.
* The overlay is a single combined overlay. The kvoice module refuses a second one (q6mvm already present), so the speaker
  overlay is applied **instead of** the audio6 one. All audio6 modes still run afterwards, because the card is bound and
  voice_dt is non-empty.
* **TFA controls:** the driver names its controls `"<container app name> Profile"`, `"… Stop"`, `"… Calibration"` and
  `"… <profile> Playback Volume"`. The container strings are NXP / TFA / 9894N1A1, so `TFA Profile` is likely, which matches
  the ROM `mixer_paths_a6l.xml` speaker path. run.sh finds the real name and prints it. If it differs, fix the XML.
* Registers (tfa9894_tfafieldnames.h, field = 0xRRBL):
  * 0x00: b0 PWDN, b3 AMPE
  * 0x03: REV
  * 0x10: b0 VDDS, b1 PLLS, b2 OTDS, b3 OVDS, b4 UVDS, b5 OCDS (clear on read), b6 CLKS, b8 NOCLK, b11 SWS, b12 AMPS
  * 0x11: b10 TDMERR
  * 0x12: b6 MANOPER
  * 0x14: b3–6 MANSTATE

  They are read with the driver's own `reg`/`rw` sysfs attributes (reads only). This is done only when the real driver
  probed; the stub has no drvdata and a read would oops.

### Pass criteria
| step | PASS | meaning when not |
|---|---|---|
| sens load | `A6L_SENS_LOAD_PASS accel gyro mag` | mag missing alone → AK09918 not in SMGR's list (check sns.reg / klog); all missing → registry/ADSP order (pre must precede ADSP) |
| flat | `A6L_IMU_ACCEL_PASS` \|g\| 9.3–10.3; `A6L_IMU_GYRO_REST_PASS` mean \|ω\| < 0.05, max < 0.15 rad/s; `A6L_IMU_GRAVITY … map OK` | map wrong → re-run with `MAP=` from the printed gravity axis (e.g. gravity on −Z → try `+x+y+z` / `-y-x+z`), report which one gives Z=+g |
| turn | `A6L_IMU_GYRO_TURN_PASS` max \|ω\| > 0.3; `A6L_IMU_MAG_PASS` = (raw \|B\| 25–65 µT **or** hard-iron-corrected horizontal radius 10–40 µT) **and** heading sweep ≥ 10/12 30° bins (raw or corrected); informative `A6L_IMU_FRAME CONSISTENT` (heading change ≈ −gyro Z) | INCONSISTENT → one mag axis sign differs from accel/gyro (note for the HAL map) |
| tilt | `A6L_IMU_TILT_PASS` accel X and Y ranges > 6 m/s² | — |
| spk load | `A6L_SPK_LOAD_PASS` and `A6L_SPK_TFA_DETECTED` | `A6L_SPK_STUB <err>`: amp not usable; card still binds; see KLOG (I²C NAK = −6/−121 → reset gpio76/L13A; revision → REV reg) |
| spk 40/20 | `A6L_SPK_TONE_PASS` (tinyplay rc 0, during playback CLKS=1 NOCLK=0 AMPS=1, no OTDS/UVDS/OCDS) **and Pierre hears the tone from the loudspeaker** | NOCLK=1 / PLLS=0 → no TERT MI2S bit clock (LPIPIN 4–7 mux, q6afe TERT clock, sd-lines); AMPS=0 with clocks → DSP/container not started (fw-state/dsp-state, "Container file not loaded"); stream error → q6afe/q6adm KLOG lines |

**Stub fallback:**
* If the amp fails, `snd-soc-tfa98xx` registers the silent `tfa98xx-aif-stub` DAI, and the card (headset, mics, voice)
  still binds. The ROM then plays nothing on the speaker, and a6l-audio-route falls back to headphones.
* The fallback does NOT cover two cases: the module failing to insmod, and the patched LPI missing. In both, the card waits
  forever and the audio6 tests are lost for that boot. If that happens, reboot and use the audio6 ovl.
* ROM fallback: the ledger's audio DT line can switch to `a6l-voice-onbase-v75` (no speaker).

## 4. Risks / unknown
* Nothing here ran on the phone. SMGR units (gauss) and the NED→Android map come from the driver source and QTI convention, and
  are checked live by `flat`/`turn`.
* The AK09918 hard iron in this phone is unknown. The raw magnitude may fall outside 25–65 µT, which is why the corrected
  radius counts too.
* The TFA9894 has never been probed on mainline. The TERT MI2S bit clock, SD line (SD1 = gpio7) and pins come from stock DT
  values only. The first tone is −40 dBFS through the stock container's default profile, which should be faint but safe.
* The ROM's sensors HAL (trout) cannot see the SMGR devices (§1). Accelerometer, gyroscope and compass inside Android need
  the sensors.a6l extension before the ROM is flashed.
