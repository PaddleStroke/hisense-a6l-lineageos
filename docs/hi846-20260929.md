**Stock runs the Hi-846 on 2 MIPI data lanes. Our DT overlay (and the ROM `a6l-camera-v75.dtso`) declares 4 lanes, so the mainline driver loads its 4-lane register set and camss expects 4 lanes. ### 2b. Stock register tables vs mainline hi846.c (script output, relay `h846-cmp1`)
- Stock `hi846_init` (212 regs) is **identical to mainline `hi846_init_2lane`** except for one register (0x0077 vs 0x0076). Both start with the same MCU firmware block `0x2000=0x100a`.
- Mainline `hi846_init_4lane` is a different set: 381 regs, firmware `0x2000=0x987a`.
- Stock res0 (3264x2448) ends with the MIPI block `0900=0320 0902=c31a 0914=c109 … 0f2a=0024`. That block is the tail of mainline `hi846_init_2lane`, so it is the Hynix full-size **2-lane** setting.
- Upstream developed and tested hi846 on the Librem 5, which uses **2 lanes**. The 4-lane tables upstream are vendor tables that nobody has verified. Our `hi846-4lane-default.patch` only exists to make them selectable.

### 2d. Clocks, CSID and routing (checked in source, no issue expected)
- **Clocks:** rom1 enables `cphy_csid1` at 200 MHz and `csi1` at 310 MHz when CSIPHY1 powers on. `csiphy_clk_src` is one RCG shared by all `cphy_csidK`/`csiphyK`, so it runs at 200 MHz as for the other two sensors. CSID0 enables its own `cphy_csid0`.
- **Routing:** CSIPHY1 → CSID0 uses the camss link. The CSID0 CORE_CTRL_1 phy_sel is `csiphy_id << 17`, which works for s5k3t1 (0x00040009). The sdm660 CSIPHY clk_mux is written with the CSID id.
- **Stock CSID:** stock uses CSID2 for this sensor. camera16 adds a CSID1 row as a routing control.
- **MCLK:** 24 MHz vs the 25 MHz the driver expects. Stock uses the same PLL registers at 24 MHz, so the link only runs about 4 % slower. This is harmless.

### R2.2 Root cause (found offline in the t37 logs, confirmed in the source): the hi846 never started streaming
Evidence in `logs/t37/kmsg-live.txt` and `c16.tar` `*.dmesg`, for every hi846 row:
1. **No `A6L_H846 ON` line ever.** camfix16 prints it right after `MODE_SELECT 0x0a00=1`.
2. **`A6L_H846 OFF … 0a00=00`** is printed **1.1 s after the row starts**, 5.5 s *before* the `VFE sof timeout`. So `hi846_stop_streaming()` ran at stream-on time.
3. Between them there is **no hi846 error line**. Every register-write failure path in `hi846_start_streaming()` would print one.
4. At stream-off there is a **`WARNING: v4l2-subdev.c:484 call_s_stream`** (`WARN_ON(sd->s_stream_enabled == !!enable)`). That means a subdev whose `s_stream(1)` returned non-zero is being stopped. The same WARN appeared in t36; the round-1 doc read it wrongly as "a consequence, not a cause".

Mechanism, from the actual 7.2.3 source:
- `hi846_set_ctrl()`: `ret = pm_runtime_get_if_in_use(dev);` returns **1** while the sensor is powered. `if (!ret || ret == -EAGAIN) return 0;` The EXPOSURE and VBLANK cases then only pass `&ret` to `hi846_write_reg_16()`. That function skips only when `*err < 0` and never clears the 1. **So s_ctrl returns 1.**
- `hi846_start_streaming()` → `__v4l2_ctrl_handler_setup()` returns 1. The function returns before the `0x0034` read and before `MODE_SELECT=1`, **with no message**.
- `hi846_set_stream()`: `if (!enable || ret) { hi846_stop_streaming(); pm_runtime_put(); }` (the OFF dump) returns **+1**.
- camss `video_start_streaming()`: `if (ret < 0 && ret != -ENOIOCTLCMD) goto error;` A +1 is treated as success. STREAMON succeeds, so camcap reports `rc=0 streaming...` while the sensor sits in standby. That gives no SOF.
- `call_s_stream()` sets `s_stream_enabled` only when `ret == 0`. The stream-off then WARNs (point 4).

The OFF-dump register values match the mainline 2-lane tables exactly (for example `0902=43 19`, `0914=c1 09`, `0f2a=41 24`, `0a12=0660`, `0a14=04c8`, `2000=100a`). That proves the I2C path, power, reset and the init/mode writes are fine. Only MODE_SELECT is never written.

**Consequences:**
- t36 (4 lanes) failed for the same reason. The lane count was never tested on a streaming sensor, so the 2-lane finding (§2) still stands on its stock evidence.
- The t29/t30 "2 SOF" were spurious, as §2c already said.
- **The ROM hi846.ko (mainline + 4-lane patch) has the same bug.** libcamera would get the same silent standby sensor.

**Fix:** `ret = 0;` after the pm_runtime check.
- `device/hisense/a6l/kernel/camera/patches/hi846-a6l-ctrlfix.patch` is the bare 1-line fix on mainline + 4-lane. Built as `extra/hi846-ctrlfix.ko`; it is not in the ROM yet.
- In camera17 it is `hi846.a6l_fix=1` (the default).
